## What a person experiences

Auto-scroll while dragging a node to a viewport edge is dead for the whole gesture whenever the pointer stops moving before a second pointermove lands — i.e. press a node, drag it into the 50px edge band in one motion, hold still, and the canvas never scrolls. You cannot drag a node to somewhere off-screen without repeatedly jiggling the pointer. When it does recover (because you kept moving), the first animation frame of every drag is silently skipped. Second half: two window keyboard listeners are removed and re-added four times per gesture (pan, box-select, connection-drag), and on every render for any consumer that passes an inline `onEntitiesChange`/`onEdgesChange` — waste, not a wrong pixel, but it is also the only thing keeping `handleKeyUp`'s `isPanning` fresh, so it is load-bearing today.

## What could regress

1. **Auto-scroll starts working where it silently did not**, so a drag that ends inside the 50px band now finishes at a different world position. The existing `drag` behaviour law is the concrete exposure and I measured its fixture: with `count=12&seed=1` the rng puts `n0` at world/screen `(5, 9)`, so `harness/behaviors.mjs:293` presses at `(45, 39)` — inside both the left and top bands — and `mouse.move(n0.x+140, n0.y+90, {steps:10})` puts step 1 at `(55, 45)`, still 5px inside the TOP band (proximity 0.10 → `scrollY = -1.5px/frame`). If a frame boundary falls inside that ~10ms gesture, `check('drag delta matches pointer travel at zoom 1', Math.abs(d.x-100) <= 2 && Math.abs(d.y-60) <= 2)` at `behaviors.mjs:306` gains up to ~1.5-3px of extra world travel and goes intermittently red. The repair is to move that fixture's press point out of the band (or drag a node that is not `n0`), NOT to widen the tolerance. Checked and NOT at risk: `drag under zoom` (viewport 60,40 @ 0.5 puts `n0` on screen at `(62.5, 44.5)`, press at `(82.5, 59.5)` — outside), `multi-drag` (asserts `d0 === d1`, which auto-scroll preserves since every dragged id gets one shared delta), `keyboard` (asserts only `x !== before.x`), `marquee` (presses at `(2,2)` but box selection never sets `dragState.current`, so `runAutoScroll` cannot run).

2. **Half 2 done naively strands the canvas in pan mode** — see the last paragraph of the fix. `lastPointerPos.current` is the exact mirror; I verified every write (948, 1153) and every clear (1141, 1665, 2089) and each clear is paired with `setIsPanning(false)`.

3. Escape semantics tighten rather than change: every `cancelConnectionDraft()`/`setSelectionBox(null)` in the file is already paired with its React setter, so the store field and the boolean only ever disagree during the batching window the swap is meant to close. Existing laws that would catch a real divergence: none today — Escape has no behaviour law, which is worth noting rather than hiding.

4. `runAutoScroll` still freezes `snapToGrid`/`snapGrid` for the duration of a self-perpetuating loop. Those do not change mid-drag, so it is not a defect, but the fix does not remove that property and should not be described as if it did.

## The law that proves it

**Law A (the defect) — `harness/behaviors.mjs`, new `auto-scroll` section.** The input is load-bearing: it must be ONE pointermove that both crosses `DRAG_THRESHOLD` (5) and lands inside `AUTO_SCROLL_EDGE_THRESHOLD` (50), followed by stillness. A multi-step drag to the edge passes with the defect present, because the second and later moves schedule a re-rendered closure whose `isDragging` is true — a law built on `{steps: 10}` is a law about the special case wearing the general case's name.

```
await withPage('count=12&seed=1', async (page) => {
  const before = await state(page);            // n0 is at screen (5, 9)
  const n0 = screenOf(before, 'n0');
  await page.mouse.move(n0.x + 40, n0.y + 30); // (45, 39)
  await page.mouse.down();
  await page.mouse.move(20, 400);              // ONE move: 5px threshold crossed AND screenX=20 (deep in the left band). steps defaults to 1.
  await page.waitForTimeout(120);
  const armed = await state(page);             // the pointer now never moves again
  await page.waitForTimeout(600);
  const after = await state(page);
  await page.mouse.up();

  check('holding a drag at the edge scrolls the viewport',
    after.viewport.x - armed.viewport.x > 50,
    `dx=${after.viewport.x - armed.viewport.x}`);
  check('the dragged node travels with the auto-scroll',
    armed.positions.n0.x - after.positions.n0.x > 50,
    `${armed.positions.n0.x} -> ${after.positions.n0.x}`);
});
```
Arithmetic: `screenX = 20` gives `leftProximity = 1 - 20/50 = 0.6`, `scrollX = -9px/frame`, so `viewport.x` grows ~9px per frame — ~324px over 600ms at 60fps, and still >50 at a software-rasterised 10fps. With the defect it is exactly 0. Read from `store.getState()` (the harness's own `state()`), which is the browser's real output, not a declared value.

**Calibration / null control, in the same section** — without it the law is satisfiable by any accidental pan and is not a law about the edge band:
```
  await page.mouse.move(640, 400);   // one move, dead centre, no band
  ... hold 600ms ...
  check('a drag held mid-canvas does not scroll', Math.abs(after.viewport.x - armed.viewport.x) < 1);
```

**Law B (the half-2 regression guard) — same file.** Its fixture must hold the mouse button DOWN across the Space release; release the button first and `handlePointerUp` clears `lastPointerPos.current` at 1665, both spellings pass, and the law measures nothing.

## What the critics said

### safety

Two things the finding overstates. (1) Impact: auto-scroll is NOT dead for the whole gesture. Once React commits the drag-start render, the onPointerMove prop at 2232 carries a FRESH runAutoScroll with isDragging === true, so every pointermove from the second onward arms a working closure and the loop self-perpetuates correctly. The live defect is narrower than "dead": the first animation frame of every drag, plus the specific gesture where the threshold crossing, entry into the 50px band and the stop all happen on one event. The user-visible paragraph describes that gesture correctly, but the headline framing and "auto-scroll is dead for the whole gesture" oversell it. (2) Regression size on the `drag` law: the estimate "gains up to ~1.5-3px and goes intermittently red" should be sharpened. topProximity at step 1 (55,45) is 0.10, so one auto-scroll frame costs exactly 1.5 world units (scrollY = -1.5, viewport.y += 1.5, entity ends 1.5 higher), giving d.y = 58.5 against a tolerance of |d.y - 60| <= 2 — that still PASSES. Going red needs TWO frames inside the gap between step 1 and step 2, i.e. roughly 33ms between two adjacent CDP mouse-move dispatches. So it is a low-probability flake on a loaded machine, not a deterministic break, and the common case (all ten steps landing inside one frame, so the first rAF reads lastScreenPos = (145,99), outside the band) produces zero extra travel. The proposed repair — move the press point out of the band rather than widen the tolerance — is still the right one, and is additionally justified on this project's own degenerate-fixture rule: the law is named "drag delta matches pointer travel at zoom 1" but presses 39px from the top edge, inside the auto-scroll band, so it is a law about a corner drag wearing the general drag's name.

### minimal

Two corrections. (1) The user-visible impact of half 1 is overstated. The stale frame sets `active=false, rafId=0` before returning, which unlocks the arming gate at 1495, so the very next pointermove re-arms with the fresh closure and the loop then self-perpetuates while in the band. In the ordinary gesture — drag continuously toward the edge, enter the 50px band while still moving, then hold still — auto-scroll works, because entry into the band happens on a move that already has the fresh closure. "You cannot drag a node off-screen without repeatedly jiggling the pointer" is wrong. The genuinely dead-for-the-gesture case requires the FIRST post-threshold pointermove to already land inside the band (press point within ~55px of an edge, or one very large move event) AND zero further pointermove for the rest of the drag. Accurate headline: the first animation frame of every drag is skipped, and a drag begun near an edge and then held still never scrolls. (2) Half 2 is not minimal or necessary and should be split out of this commit. It has no correctness consequence — teardown and re-registration occur in the same synchronous effect flush so no key event can be dropped, and the closures' deps are correct today; the finding itself concedes "waste, not a wrong pixel". It buys four addEventListener/removeEventListener calls per gesture, which is not a per-frame cost and is invisible to every instrument this repo owns (counts.mjs measures commits, draw calls, instances, allocations per frame). It costs two new refs, a new useEffect, an Escape refactor across three conditions, and carries the item's only real regression risk (the pan-mode strand). Its stated precedent is weak: `onFileDropRef.current = onFileDrop` at 1946-1947 is a render-body ref write that the audit itself flags as #86, so the fix must invent a variant rather than reuse a pattern, and there is no useLatest/useEventCallback helper in the package (hooks/ holds only index.ts, use-graph.ts, useThemeTokens.ts). If any of half 2 ships, do only the smaller half — mirror `onEntitiesChange`/`onEdgesChange`, the unbounded per-render churn source — and leave the three booleans, whose churn is bounded at ~4 per gesture and which are load-bearing. That drops both risky edits. For the record, the mirrors half 2 relies on do hold if it ships anyway: isPanning ≡ lastPointerPos.current !== null (writes 948/1153, clears 1141/1665/2089, each clear paired with setIsPanning(false), ref read nowhere outside the pan path at 1108/1133/1149/1663), isConnecting ≡ connectionDraft (968), isBoxSelecting ≡ selectionBox (1436-1441).
