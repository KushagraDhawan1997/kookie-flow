That guard is the ONLY gate. `document.activeElement` is never read anywhere in the file (`grep -n "activeElement" src/components/kookie-flow.tsx` → no hits). Every keydown anywhere in the host document whose target is not INPUT/TEXTAREA/contentEditable — `<body>` (the default), `<button>`, `<a>`, `<select>`, a `role="option"` div, any custom control — runs the full body:

  - `:2008` `if (e.code === 'Escape')` — deselects / stops editing / cancels the connection draft from anywhere on the page.
  - `:2022` `if (e.code === 'Delete' || e.code === 'Backspace')` — deletes selected entities AND edges and fires `onEntitiesChange?.(entityChanges)` / `onEdgesChange?.(edgeChanges)` at the consumer.

## What a person experiences

A host page embedding `<KookieFlow>` loses five keys everywhere on the page, not just over the canvas. Typing a bare `t` with focus on `<body>` (the state on every page load) creates a text entity and opens its editor. Backspace or Delete with focus on any host button, link or `<select>` deletes the selected entities and edges and emits `onEntitiesChange`/`onEdgesChange` to the consumer. Space stops scrolling the host page, cancels a focused button's activation and cancels a `<select>`'s dropdown, and silently arms the canvas's pan mode. Ctrl/Cmd+A stops selecting the host page's text and selects every entity instead. Escape clears the graph selection from anywhere. The library's own toolbar is inside the blast radius: pressing Space on the aspect-lock toggle (`toolbar.tsx:876`) or any of the six segmented items does not toggle it, it puts the canvas in pan mode. Reproducible today at `apps/docs/src/app/demo-webgl` — focus the node-count `<select>`, press Space, the dropdown does not open.

## Proposed fix

TWO lines in two files. Neither alone is sufficient.

HALF A (#20) — `src/components/kookie-flow.tsx`, insert at :1994, directly after the existing early return:

    // The canvas owns these keys only while it has focus. Matches the requireFocus gate the
    // package's own useKeyboardShortcuts plugin already carries (useKeyboardShortcuts.ts:147-152).
    if (!containerRef.current?.contains(document.activeElement)) return;

`containerRef` is `InputHandler`'s own ref (declared `:559`, attached `:2208` to the `tabIndex={0}` div at `:2207-2244`) — the element that actually receives focus, because a left-click on the canvas hits the non-focusable `<canvas>` and Chrome walks up to the nearest focusable ancestor. Verified there is no `preventDefault()` on that path: the only one in `handlePointerDown` (`:931-1089`) is at `:946`, in the middle-click / space-pan branch.

Gate `handleKeyDown` ONLY. Do NOT gate `handleKeyUp` (`:2084-2092`) — it is a reset (`setIsSpaceDown(false)`), and gating it strands `isSpaceDown === true` forever if focus leaves the canvas while Space is held, leaving the canvas permanently in grab-cursor pan mode.

HALF B (#48) — `src/components/toolbar.tsx:363`, one line beside the existing pointer fence:

    onPointerDown={(e) => e.stopPropagation()}
    onKeyDown={(e) => e.stopPropagation()}

Copied verbatim from `widgets-layer.tsx:486`, which already does this. Half A cannot cover this: `<Toolbar/>` is a DOM descendant of the gated container, so `contains(document.activeElement)` is true for a focused toolbar button. React attaches its delegated listeners at the root container, which is deeper in the tree than `window`, so the synthetic `stopPropagation()` calls through to `nativeEvent.stopPropagation()` and the window listener never runs.

ONE MORE LINE WORTH TAKING WITH THEM (optional, closes the last dead-shortcut path): `kookie-flow.tsx:946`, the middle-click branch, calls `e.preventDefault()` on pointerdown, which suppresses the compatibility mousedown and therefore focus. A user whose first canvas gesture is a middle-click pan never focuses the container and gets no shortcuts. `containerRef.current?.focus({ preventScroll: true })` at the top of `handlePointerDown` fixes it.

DO NOT instead widen the tagName guard to `BUTTON`/`SELECT`/`A`. It is an unbounded list (`role="option"` divs, `tabindex` divs, web components) and it does not fence `<body>`, which is where `KeyT` does its damage.

## What could regress

This is the audit's `sign-off` item — it changes what the keyboard does — and the existing suite cannot see either the defect or the repair, so nothing catches these automatically today.

1. SHORTCUTS GO DEAD UNTIL THE FIRST CANVAS CLICK. `document.activeElement` is `<body>` on load, and `container.contains(body)` is false. Every current single-flow demo where the canvas fills the page gets a behaviour change on first paint. This is the sign-off. Nothing in the repo would catch it: `behaviors.mjs:418`'s Ctrl+A is preceded by a drag at `:409-412` that focuses the container first, so the one existing keyboard law passes either way.

2. "ESCAPE TO DESELECT AFTER USING THE TOOLBAR" DIES (half B, named by the audit). The toolbar only renders when there is a selection (`toolbar.tsx:355` `if (!visible || !toolbarContent)`), so after pressing a toolbar control the user's focus is on a control whose only dismissal today is the window Escape. The fence removes it. If that is unacceptable, the fence must re-emit Escape rather than swallow it — decide it, do not discover it.

3. TOOLBAR CONTROLS START WORKING, WHICH CHANGES PIXELS. Space on the aspect-lock `ToggleIconButton` (`toolbar.tsx:876`) and on the six `SegmentedControl.Item`s currently does nothing but pan; after the fence it toggles and mutates entity data through `batchUpdate`. That is the repair, but it is a behaviour change on a control a user may have learned is inert.

4. MIDDLE-CLICK-FIRST LEAVES THE CANVAS UNFOCUSED FOREVER — `:946`'s `preventDefault()` on pointerdown suppresses focus. Without the optional `.focus()` line, a middle-click panner never gets keyboard.

5. A SYMMETRIC GATE ON `handleKeyUp` STRANDS PAN MODE (see minimalFix). Note the pre-existing sibling of this: nothing clears `isSpaceDown` on window blur, so alt-tabbing with Space held already strands it. Do not make it worse.

6. SEQUENCING WITH C36. The audit: "v2's `Toolbar` carries `role='toolbar'` with a roving tab stop, which collides with C28's key routing — sequence them." Land C28 first; the roving tab stop moves focus between toolbar buttons with arrow keys, and a fence written against the v1 markup must be re-verified against v2's composite.

7. THE PORTAL CASE IS DELIBERATELY OUT OF SCOPE AND MUST STAY THAT WAY. The audit's §6: "Whether React 19 routes a keydown from Radix's portalled Select listbox through the widget wrapper's React-tree `onKeyDown` fence… could not be settled by reading and must be measured. #48 is scoped to the toolbar for that reason." The font-weight `Select.Root` at `toolbar.tsx:798` portals its listbox out of the toolbar's DOM subtree. Do not claim the fence covers it without measuring.

8. MULTI-INSTANCE. Two mounted flows each register a window listener (`harness/fixture/app.tsx:486` mounts N). Today both react to every key; after the fix only the focused one does — correct, and a visible change for the reentrancy fixture.

## What the critics said

### safety

The defect is real, but the fix as written must not land: it introduces a silent dead-keyboard state in the flagship workflow, and that regression is not in the finding's regression list.

THE UNNAMED REGRESSION. `document.activeElement` falls back to `<body>` whenever a focused descendant of the flow UNMOUNTS, and the flow does that routinely with no pointer event involved. Verified chain:

1. `src/components/text-edit-overlay.tsx:381` — `if (!editingId) return null;`. The editor's `<textarea>` is UNMOUNTED on exit, not hidden.
2. `src/components/text-edit-overlay.tsx:180-183` — Escape inside the editor calls `preventDefault()` then `commitAndExit()`, which clears `editingEntityId` and triggers that unmount.
3. `grep -rn "\.focus(" src/` returns exactly three hits — `text-edit-overlay.tsx:94`, `text-edit-overlay.tsx:372`, `kookie-flow.tsx:1860` — and ALL THREE are on the textarea (`ta.focus()` / `textareaRef.current?.focus()`). Nothing in the package ever calls `containerRef.current.focus()`.
4. Removing the focused element resets `document.activeElement` to `<body>` in every engine, so `container.contains(document.activeElement)` is false.

Result: `T` → type → `Escape` — the exact sequence the finding cites as the flagship damage — leaves the canvas keyboard-dead under the gate. Delete, Ctrl+A, Space and Escape all stop, silently, with no cause visible to the user. TODAY that sequence works, because `activeElement` is `<body>`, `tagName === 'BODY'`, and the existing guard passes it through. So this is a regression the fix creates, not a pre-existing one. Same for any consumer calling the imperative `stopEditing()`.

WHY THE FINDING'S OWN MITIGATIONS DO NOT REACH IT. Regression #4 and the optional third line (`containerRef.current?.focus({preventScroll:true})` at the top of `handlePointerDown`) are a POINTERDOWN hook, and this strand happens with no pointer event at all. Regression #1 is "dead until the first canvas click" — a first-paint condition; this is a dead state that RE-ARMS after every text edit, mid-session, and a reviewer signing off on #1 would not expect it. The click-away exit self-heals (the click lands on the canvas and focuses the container) and the click-another-entity exit self-heals (`kookie-flow.tsx:1870`'s `stopEditing()` runs inside a pointerdown whose default action focuses the container); ONLY the Escape path strands, which is why reading the pointer paths does not surface it.

WHAT WOULD MAKE IT LANDABLE. One more line: focus the container when editing exits without a pointer gesture — `containerRef.current?.focus({preventScroll:true})` (or the equivalent inside `commitAndExit`), plus a law that presses T, types, presses Escape, then presses Delete and asserts the entity is gone. Without that, the gate converts a host-page nuisance into a library that loses its own keyboard.

TWO OBJECTIONS I RAISED AND KILLED, so they are not re-raised. (a) Half B does NOT break Radix dismissal: `@radix-ui/react-use-escape-keydown` (read at node_modules/.pnpm/@radix-ui+react-use-escape-keydown*) registers on `ownerDocument` with `{ capture: true }`, so a bubble-phase `stopPropagation()` at the toolbar root cannot reach it — the portalled Select still closes on Escape, and the toolbar's own Radix arrow/Enter handlers sit below the root in the React tree and run first. (b) No performance-rule violation: `document.activeElement` + `Node.contains()` is O(ancestor depth), allocates nothing, forces no layout, and keydown is not a pan/zoom/drag hot path.

NO EXISTING LAW BREAKS EITHER WAY, which is the point: `behaviors.mjs:418`'s Ctrl+A is preceded by the drag at `:409-412` that focuses the container, and `grep` over the ten `src/**/*.test.ts` files finds no keyboard test. The suite is blind to the defect, to the repair, AND to this regression.

TWO SECONDARY CORRECTIONS. (1) "THE PACKAGE ALREADY OWNS THE GATE IT IS MISSING" overstates the precedent: `useKeyboardShortcuts.ts:120` defaults `requireFocus = false`, and the gate at `:148` is double-conditional (`requireFocus && containerRef?.current`), so the package's own plugin ships UNFENCED by default. The mechanism exists; the precedent for turning it on does not. (2) Half B removes Delete/Backspace from a focused toolbar control as well as Escape — the finding names only Escape under regression #2, and Delete-after-touching-the-toolbar is at least as plausible a gesture.

### minimal

HALF B IS NOT MINIMAL AND NOT GENERAL — one line in ONE file does strictly more.

Gate on the event target instead of on containment, in `kookie-flow.tsx` at :1994:

    if (e.target !== containerRef.current) return;

A keydown targets `document.activeElement`, so this is true exactly when the canvas container itself has focus. It subsumes Half A (body/select/host button all fail it) AND Half B (a focused toolbar button is the target, not the container), in one place, with no second file touched.

Three concrete ways it beats the proposed pair:

1. It closes a hole the proposed fix leaves open. `contains(activeElement)` passes for EVERY focusable descendant of the container, and consumer `children` render inside it (verified path above). A host that renders its own control panel as `<KookieFlow><MyPanel/></KookieFlow>` still has Space, Backspace and `t` stolen from its buttons after the fix, and the only remedy on offer is another per-component `onKeyDown` fence. That is the same unbounded-list objection the finding itself raises against widening the tagName guard, re-committed one layer out.

2. It is markup-agnostic, which matters for the finding's own sequencing note (#6/C36). A fence written onto `toolbar.tsx:363` is a claim about v1's toolbar root; v2's `role="toolbar"` composite with a roving tab stop obliges re-verifying it. A target-equality gate in the input handler needs no re-verification when the toolbar's markup changes, because it never mentions the toolbar.

3. It removes the "does React's stopPropagation reach the window listener" question entirely. The finding's reasoning there is sound (React's root-level dispatch calls `nativeEvent.stopPropagation()`, and window is later in the bubble path than any React root container), but it is a bet on React's dispatch internals that the one-liner does not have to make — and the finding's own §7 already concedes the portalled `Select.Root` at `toolbar.tsx:798` cannot be settled by reading. Target equality gates the portalled listbox correctly for free, since a portalled option is not the container either.

Two things the target-equality form does NOT change: the Escape-after-toolbar regression (#2) is identical under both — it is caused by gating at all, not by where — and it must still be decided rather than discovered. And `handleKeyUp` must stay ungated for the reason the finding gives.

SECOND CORRECTION: the `.focus({preventScroll:true})` line is filed as "optional" and should be mandatory, under either gate. The whole gate rests on click-focus reaching a `tabindex=0` div, which the finding argues only for Chrome; `:946`'s `preventDefault()` already breaks it for a middle-click-first user by the finding's own account, and making focus explicit at the top of `handlePointerDown` is what makes the gate's precondition a fact rather than a browser behaviour. It also shrinks regression #1's blast radius to first paint only.

MINOR: the citation of `useKeyboardShortcuts.ts:147-152` as "the package already owns the gate it is missing" reads as if the mechanism were reusable. It is a public plugin hook with a different API surface; anyone acting on that sentence by trying to route `handleKeyDown` through it would be rewriting six branches that read `e.repeat`, `isConnecting`, `isBoxSelecting` and the store. Copy the two lines, do not reach for the hook.
