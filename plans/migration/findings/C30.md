## What a person experiences

Two things, and the second is bigger than the audit recorded.

(1) Today, on the public API: `<KookieFlow entityStyle={{ background: '#1e1e1eaa' }} />` paints every entity opaque mid-grey (128,128,128) instead of near-black. Same for `entityStyle.borderColor`. The prop's own JSDoc says "CSS color", and `#rrggbbaa` is one. Silent — the parser's `console.warn` is on a branch this path never reaches. `hexToRGB`, `parseColorToRGB` and `parseColorToRGBA` are all public exports (`src/index.ts:56-59`), so a consumer calling them directly gets the same answer.

(2) On the theme path: `--gray-a3`, `--gray-a6` and `--accent-a3` reach `useThemeTokens` as `[0.5, 0.5, 0.5, 1]` on an sRGB display and as their real values on a P3 display. No renderer consumes those three yet, so no pixel moves today — but the values are handed to consumers through the public `useThemeTokens()` hook, and they are constant across a light/dark flip on sRGB (both `#0000000f` and `#ffffff12` collapse to mid-grey), so they contribute nothing to `tokensEqual` (`useThemeTokens.ts:515-530`) change detection. C34 wires v2's `--tone-a*` roles into the render path; at that point (2) becomes (1) for every alpha surface in the canvas.

## Proposed fix

Two edits in `src/utils/color.ts`. One alone is half a fix.

1. Replace `hexToRGB` (lines 132-150) with an RGBA core, keeping the public RGB signature and the mid-grey fallback:

```ts
const HEX_RE = /^([a-f\d]{2})([a-f\d]{2})([a-f\d]{2})([a-f\d]{2})?$/i;

export function hexToRGBA(hex: string): RGBAColor {
  const s = hex.startsWith('#') ? hex.slice(1) : hex;
  // Expand shorthand: rgb -> rrggbb, rgba -> rrggbbaa
  const n = s.length === 3 || s.length === 4
    ? s.split('').map((c) => c + c).join('')
    : s;
  const m = HEX_RE.exec(n);
  if (!m) return [0.5, 0.5, 0.5, 1];
  return [
    parseInt(m[1], 16) / 255,
    parseInt(m[2], 16) / 255,
    parseInt(m[3], 16) / 255,
    m[4] === undefined ? 1 : parseInt(m[4], 16) / 255,
  ];
}

export function hexToRGB(hex: string): RGBColor {
  const [r, g, b] = hexToRGBA(hex);
  return [r, g, b];
}
```
(Slicing the `#` off first also closes a smaller pre-existing hole: `hexToRGB('fff')` currently misses the `length === 4` test and falls to mid-grey, while the old regex's `#?` claims hashless input works.)

2. Line 326-330 becomes:
```ts
  // Handle hex, including #rgba and #rrggbbaa
  if (trimmed.startsWith('#')) {
    return hexToRGBA(trimmed);
  }
```

3. Amend the three JSDoc lines (130, 264, 316) to name the 4- and 8-digit forms — otherwise the fix ships with doc–code drift in the same file.

Do NOT export `hexToRGBA` from `src/index.ts` unless someone asks; the two internal call sites are enough and the public surface stays as it is.

## What could regress

1. **The one that actually changes a pixel, and it is not a full repair.** `parseColorToRGB('#1e1e1eaa')` goes from `[0.5,0.5,0.5]` to `[0.118,0.118,0.118]` — the *unpremultiplied* colour, alpha dropped. In `style-resolver.ts:290` the alpha is not read from the parsed colour at all; `backgroundAlpha` is derived from the variant, `const backgroundAlpha = variant === 'ghost' || variant === 'outline' ? 0 : 1;` (style-resolver.ts:298-299). So an alpha-hex `entityStyle.background` goes from opaque mid-grey to opaque dark — visually a *larger* change, and still not what the string means. C30 fixes the parse, not the plumbing; routing `parseColorToRGBA` into `ResolvedEntityStyle.backgroundAlpha` is a separate change. Say so in the commit, or someone will claim C30 shipped transparent entity backgrounds.

2. `hexToRGB` is a public export (`src/index.ts:57`). Its answer for 8-digit input changes. No in-tree consumer depends on the old mid-grey; `grep` shows the only callers are `parseColorToRGB`/`parseColorToRGBA` and `rgbToHex`'s neighbours.

3. `--gray-a3`/`--gray-a6`/`--accent-a3` start moving on a theme flip where they were previously pinned at `[0.5,0.5,0.5,1]`, so `tokensEqual` (`useThemeTokens.ts:515-530`) stops swallowing changes it was swallowing. That means strictly *more* theme re-resolutions, which is the correct direction; no renderer reads those three, so no pixel moves.

4. Existing laws that would catch a botched fix: `src/utils/color.dom.test.ts:74-75` pins `#808080` → 128,128,128 and `#f0a` → 255,0,170. A shorthand-expansion mistake in the new `hexToRGBA` fails on `#f0a` immediately. `harness/spikes/color-formats.mjs:73-74` runs the same two through a canvas readback.

5. Nothing in the harness or the 196 unit laws asserts the old behaviour, so nothing goes red for the wrong reason.

## The law that proves it

**Law A — node/jsdom tier, added to `src/utils/color.dom.test.ts` (the file that already owns this function). This is the load-bearing one and it needs no browser, which matters because headless Chromium reports sRGB and never enters the `@media (color-gamut: p3)` block.**

Assert absolute values computed independently of the parser (`0x0f/255`, not a number retyped from the parser's own arithmetic):

```ts
expect(parseColorToRGBA('#0000000f')).toEqual([0, 0, 0, 0x0f / 255]);      // v1 light --gray-a3
expect(parseColorToRGBA('#ffffff12')).toEqual([1, 1, 1, 0x12 / 255]);      // v1 dark  --gray-a3
expect(parseColorToRGB('#0000000f')).toEqual([0, 0, 0]);
expect(parseColorToRGBA('#1234')).toEqual([0x11/255, 0x22/255, 0x33/255, 0x44/255]);
```

**The fixture is the load-bearing half.** `#0000000f` alone is a degenerate input for the general case: its RGB is `[0,0,0]` and its 6-digit prefix `#000000` reads `[0,0,0]` too, so a truncating fix gets the triple right. `#1234` is the input where the general case and the special case give different answers — truncated to `#123` it reads `[0.067, 0.2, 0.2]` against the correct `[0.067, 0.133, 0.2, 0.267]`, so the green channel disagrees. And the *alpha* must be asserted, not just the triple — that is the assertion that reaches site 2.

**The precise sabotages that must make Law A fail:**
- (a) Restore the shipped regex `/^#?([a-f\d]{2})([a-f\d]{2})([a-f\d]{2})$/i` at `color.ts:139` → every case reads mid-grey: `expected 0.5 to be 0`.
- (b) **Fix site 1 only.** Put `return [rgb[0], rgb[1], rgb[2], 1];` back at `color.ts:328`. The triples are all correct and only the alpha is wrong: `expected 1 to be 0.058823…`. A law asserting only the RGB triple survives this sabotage — run it, or the RGBA entry point is unproven.
- (c) Truncate instead of parse (`normalizedHex.slice(0, 7)`) → fails (b)'s alpha assertion, and `#1234` additionally fails on green.
- (d) Delete the 4-digit arm of the shorthand expansion → `#1234` reads mid-grey while all three 8-digit cases still pass.

**Law B — browser tier, `harness/spikes/color-formats.mjs`. The gamut half, against a mechanism that is not the parser.**

Add `{ name: 'hex + alpha', value: '#0000000f' }` to the `cases` array (lines 72-81) and let the existing canvas-readback `truth()` answer it; the file's `isFallbackGrey` verdict (line ~119, `const GREY = [128, 128, 128]`) already names exactly this failure mode. Then add, beside the existing alpha probe at line 111, the cross-spelling agreement that only a real browser can run — Chromium resolves `color(display-p3 …)` through the `color-mix` probe regardless of the display's gamut, so both live code paths execute:

```js
const hexA  = window.__harness.lib.parseColorToRGBA('#0000000f');
const p3A   = window.__harness.lib.parseColorToRGBA('color(display-p3 0 0 0 / 0.063)');
```

**Two traps this law must be built around, both of which would otherwise make it green over a broken parser:**
- *Vacuity guard, mandatory.* Assert `p3A` is not `[0.5, 0.5, 0.5, 1]` BEFORE comparing. The audit's phrasing ("assert they agree") is not sufficient on its own: in jsdom both sides fall through to mid-grey and agree perfectly, which is why Law A states absolute values rather than an agreement.
- *Do not assert exact equality.* Radix authors the two spellings independently — `#0000000f` is alpha 0.05882 and the P3 form is 0.063, and `--gray-a6` is 0.14902 against 0.153. An exact-equality law fails on correct code. Tolerance ≈0.01 on alpha, 1/255 on the channels.

Honest limit, to be written into the law's comment rather than glossed: headless Chromium reports sRGB, so the `@media (color-gamut: p3)` branch itself never fires and "the same token resolves to two colours by display gamut" is not directly measurable in this harness. Law B measures the two *spellings* agreeing, which is the strongest available proxy; the gamut switch is proven by reading `harness/dist/kookie-ui.css:312` against `:1153`.

## What the critics said

### exists

One supporting claim is wrong and should be corrected before this becomes a commit: the finding states "This is the one hex-parsing site in the package (`grep 'a-f\d'` returns only `color.ts:139`)". That grep was for the regex character class and missed a second, independent hex parser — `parseColor` at `src/utils/text-layout.ts:181-192`, which does `color.slice(1)` + `parseInt(hex, 16)` + shift-and-mask and expands only 3-digit shorthand. It is 8-digit-blind too but fails DIFFERENTLY: `#1e1e1eaa` yields `[30/255, 30/255, 170/255]` (it reads the G/B/A bytes as R/G/B) rather than mid-grey, and above 0x7fffffff the ToInt32 coercion in `>>` makes it wronger still. Callers are `text-layout.ts:390,816,968` over an internal `entry.color` typed "hex or rgb string"; I did not trace whether consumer-supplied hex reaches it, so its user-visible impact is unassessed. This does not change C30's existence or the proposed two edits, but the fix should either state that `text-layout.ts` is deliberately out of scope or add a source law naming it (the `socket-geometry-home.test.ts` pattern) — otherwise the package still ships a second private hex parser that disagrees with the repaired one.

### safety

Three corrections, none of which makes the fix unsafe.

1. REGRESSION NOTE 3 IS WRONG, in the fix's favour. It claims the fix means "strictly more theme re-resolutions" because the three alpha tokens stop being pinned at [0.5,0.5,0.5,1]. `tokensEqual` (useThemeTokens.ts:516) short-circuits on `if (a.appearance !== b.appearance) return false` BEFORE the loop, so a light/dark flip already returns false and those tokens were never swallowing it. An accent change moves `--accent-3`, `--accent-9`, `--accent-10` and `--accent-a3` in the same read, so the solid accent tokens already trip the compare. I could construct no case where the three alpha tokens are the sole differing entry. The fix adds ZERO re-renders, not more — which removes the only performance-flavoured objection to it.

2. THE FIX MARGINALLY WIDENS THE THROW SURFACE OF A PUBLIC EXPORT. `hex.startsWith('#')` throws on any non-string, where the old `hex.length === 4` tolerated some: `hexToRGB(0xfff)` returns mid-grey today and TypeErrors after the fix (null/undefined throw in both). Reachable only by an untyped JS consumer of `src/index.ts:57`. Cheap to close with `hex.charCodeAt(0) === 35` or a `typeof` guard; not a blocker.

3. THE FIX DOES NOT CLOSE THE SILENCE THE FINDING CORRECTLY NAMES. `console.warn` (color.ts:297/~340) still cannot fire for a malformed hex, because the `#` branch returns before reaching it: `parseColorToRGB('#12345')` stays a silent mid-grey before and after. The fix shrinks the silent set, it does not close it — worth one line in the commit so the next audit does not re-raise it as new.

Also worth stating in the commit alongside the note the finding already asks for: the fix changes `hexToRGB('fff')` (hashless shorthand) from mid-grey to [1,1,1] and `hexToRGB('abcd')` from the mangled `#bbccdd` — the old `length === 4` branch drops char 0 on hashless input — to the correct RGBA. Both are repairs of latent nonsense, and neither has an in-tree caller, since both call sites test `startsWith('#')` first.

### minimal

Two scope notes for the commit, neither large enough to change the verdict:

1. The proposal's slice-the-`#`-first spelling also changes behaviour for hashless input (`hexToRGB('fff')` goes from mid-grey to white). That is a second behaviour change riding along. It is defensible — the old regex's `#?` already claimed hashless input works, so this is reconciling code with its own stated contract rather than new surface — but it is not required by C30 and should be named in the commit message rather than shipped silently.

2. Priority framing: the finding's ordering (public-API impact first, theme path second) is right, but the public-API half only fires if a consumer passes an alpha hex, and no in-tree caller does. The half that is unconditionally true today is the gamut divergence at useThemeTokens.ts:390,391,397 — same token, two answers by display. That is the part that cannot be argued away as hypothetical, and it is also the part C34 turns into pixels.
