## What a person experiences

Two things a person sees, both on the frames right after a large selection or during a pan.

1. Selection outlines paint in growing batches instead of at once. Select ~1000 entities (Cmd-A or a box-select release) and the accent outlines appear on 64 of them, then 96, then 144, 216, 324, 486, 729, then all — eight frames, ~130ms on a 60Hz display, and each of those frames tears down and rebuilds the outline InstancedMesh. It reads as the selection "filling in".

2. All text blinks out for at least one frame per capacity step while panning into a label-dense region. text-renderer.tsx:171 `return;` skips the buffer populate on the growth frame, and `key={capacity}` then remounts the glyph mesh, so `mesh.count` is stale/zero across the remount — every node label, socket label and edge label at once, not one label.

Internally: React commits and full GPU buffer reallocations land inside the frame loop during pan and drag, which is the project's first rule. `text-entities.tsx` (multi-line text entities) has the same defect but its user-visible cost is unverified here, because the harness fixture never builds one — see the fixture note in proofLaw.

## Proposed fix

Two independent changes. Land them together; the second alone leaves the ramp, the first alone leaves eight deferred commits instead of eight synchronous ones.

FIX 1 — defer, by copying sockets.tsx verbatim into all three files.

In each of entity-selection.tsx (twice, once per mesh), text-renderer.tsx and text-entities.tsx, add beside the existing refs:
```ts
const pendingCapacityRef = useRef<number | null>(null);
const capacityRafIdRef = useRef<number | null>(null);
```
add the unmount cleanup that sockets.tsx:271-279 already has:
```ts
useEffect(() => () => {
  if (capacityRafIdRef.current !== null) {
    cancelAnimationFrame(capacityRafIdRef.current);
    capacityRafIdRef.current = null;
  }
}, []);
```
and replace each bare `setX(...)` with the sockets.tsx:661-674 body — `newCapacity > pendingCapacityRef.current` keeps the max, the `capacityRafIdRef.current === null` guard collapses repeated requests into one rAF.

Keep the `return;` at text-renderer.tsx:171 and text-entities.tsx:151 for now. The audit's own advice, and correct: dropping it turns "all text lags one frame" into "individual labels cut off mid-run", which is a pixel change that wants its own judgement. entity-selection needs no equivalent — it already falls through to `outlineMesh.count = Math.min(outlineCount, outlineCapacity)` at :431.

FIX 2 — size the outline mesh from what was NEEDED, not from what fit. entity-selection.tsx:364-370, split the counter:
```ts
      let outlineCount = 0;   // instances actually written
      let outlineNeeded = 0;  // instances that asked to be written
      const maxOutline = outlineCapacity;

      const writeOutline = (entity, isSelected) => {
        if (hiddenEntityIds.has(entity.id)) return;
        ...width/height and the four frustum tests, unchanged...
        outlineNeeded++;
        if (outlineCount >= maxOutline) return;   // moved BELOW the count
        ...the matrix and attribute writes, unchanged...
        outlineCount++;
      };
```
and at :416:
```ts
      if (outlineNeeded > outlineCapacity) {
        setOutlineCapacity(Math.ceil(outlineNeeded * BUFFER_GROWTH_FACTOR));   // via the rAF from FIX 1
      }
```
Note `>` not `>=`: today an exactly-full buffer grows for nothing. Line :431 `outlineMesh.count = Math.min(outlineCount, outlineCapacity)` is unchanged and still correct.

The hidden/culling tests must move above the capacity guard, which costs nothing — the `for (const entityId of selectedEntityIds)` loop at :404 already visits every selected entity either way.

Optional, same commit, one line each: route text-renderer.tsx:565/:596 and text-entities.tsx:447 `setHasSemiboldEntries` through the same rAF, so panning a semibold label across the viewport edge stops mounting and unmounting a `<TextWeightRenderer>` per crossing.

## What could regress

1. Missing the unmount `cancelAnimationFrame` is the easiest way to get this wrong — a pending rAF fires `setCapacity` after unmount. sockets.tsx:271-279 is the shape; it must be copied, not assumed.

2. FIX 2 makes the outline mesh honour the real selection size for the first time. Today `maxOutline` silently caps it; after the fix a select-all of 50k entities allocates a 75k-instance outline mesh (75k * 16 floats of matrix + 5 floats of attributes ≈ 6.3MB) where it previously allocated whatever the ramp had reached. This is correct — the handle path at :467 has always done exactly this — but it is a real memory change at the scale the migration targets, and it is the reason to land C17's culling first if it is landing at all: the frustum tests inside `writeOutline` are what keep `outlineNeeded` bounded by what is on screen rather than by the selection.

3. The mesh remount now happens on a rAF boundary rather than inside the frame callback, so `attachOutline` (entity-selection.tsx:331) and the `useEffect([buffers])` reset of `lastEntriesRef` (text-renderer.tsx:129) run one tick later. In text-renderer the interlock is delicate: `lastEntriesRef.current = entries` is assigned at :163 BEFORE the capacity check at :169, so during the pending window every subsequent `useFrame` early-returns on `entries === lastEntriesRef.current` and draws nothing new until the `[buffers]` effect resets the sentinel. That is stable and no worse than today, but it means the blank window is now two frames rather than one — which is the argument for revisiting the `return;` once law 2 below exists.

4. Fixes 7-9 in audit-findings.md were exactly this family of mesh-reconstruction bugs, and finding 9 was in this file, found only by a light→dark→light round trip. Any change to when `attachOutline` runs must be re-checked against that round trip, not against a single flip.

5. `neededCapacity = selectedEntityIds.size * 8` at :467 ignores culling, `hiddenEntityIds` and `entity.resizable === false`, all of which the loop below it honours — so it over-grows (1000 selected entities off screen buys a 12000-instance handle mesh drawing zero handles). Adjacent, not C18, and FIX 2's `needed` counter is the pattern that would close it if someone wants it.

## The law that proves it

LAW 1 (the one that bites) — the selection paints in ONE step. In harness/behaviors.mjs, count outline pixels PER FRAME, not once at the end.

Load the fixture at `count=1000`, zoom out so well over 64 selected entities are on screen simultaneously (see the fixture note below — this is load-bearing), then `window.__harness.store.getState().selectEntities(allIds)`. For each of the next 10 rAFs, do a full-backbuffer `gl.readPixels(0, 0, w, h, ...)` and count pixels matching the selection outline colour, resolved through the library's own reader — `window.__harness.lib.resolveColorToRGB('var(...)')` for `THEME_COLORS.entitySelection.selected` — never a restated hex. That machinery already exists at behaviors.mjs:466-500, where the socket-dot law reads the backbuffer and resolves the palette through the token reader for the same reason.

Assert: `firstNonZero >= 0.95 * finalCount`. The selection appears whole on the first frame that shows any of it.

VACUITY GUARD, mandatory, and it is the general-vs-special rule: first assert `finalCount` is at least ~4x the pixel area of 64 outlines. With 64 or fewer selected entities visible, ramp and no-ramp give the SAME answer and the law is green against broken code. The fixture must therefore put >64 selected entities in the viewport, each large enough that its outline is several pixels wide — a `fitView` or an explicit zoom-out before the select, not the default camera.

SABOTAGE THAT MUST MAKE IT FAIL: restore the saturating guard — move `if (outlineCount >= maxOutline) return;` back above `outlineNeeded++` at entity-selection.tsx:369 and change :416 back to `if (outlineCount >= outlineCapacity)`. Pre-fix, frame 1 shows 64/1000 of the outlines: the assertion fails at roughly `expected 0.064 to be >= 0.95`. A second sabotage — delete only the rAF deferral, keeping FIX 2 — must NOT fail this law, and that is worth recording in the law's comment so nobody later reads it as proving the deferral.

LAW 2 (the deferral) — React commits over a select-all. In harness/spikes/counts.mjs, add a scenario after `drag-node`: `mark('select-all')`, call `selectEntities(all)` through `page.evaluate`, wait ~500ms, read `reactCommits().marks['select-all']`. Assert `<= 1`. counts.mjs:133-159 already refuses to report a dead React counter, so this inherits its calibration.

SABOTAGE: revert both fixes. The counter reads 8 (one commit per ramp step) against a bound of 1.

HONEST LIMIT, and it should be written into the law rather than discovered later: a commit COUNT cannot separate "committed from inside useFrame" from "committed one rAF later" when it is a single growth — React 18 batches either into one commit. Law 2 catches the ramp; it does not catch the deferral in isolation. The deferral's own justification is that it collapses several same-frame growths into one and matches sockets.tsx, which is a structural argument, not a measured one. Record it as unmeasured in the same register audit-findings.md uses for fixes 11 and 17, rather than claiming a number.

LAW 3 (only if the `return;` half is ever landed) — no frame between two text-bearing frames is textless. Pan from a sparse region into a dense one on a fresh load (capacity starts at MIN_CAPACITY 512, text-renderer.tsx:53) and count glyph-coloured pixels per frame. Assert no zero frame is bracketed by non-zero frames. Today this FAILS on correct-by-C18's-definition code, because of `return;` + the `key={capacity}` remount — which is precisely the instrument that should decide whether that half lands, and why it should not land blind.

## What the critics said

### exists

Two narrowings that survive verification and should be carried into the fix, neither of which kills the finding:

1. The outline ramp only fires when at least `outlineCapacity` selected entities survive BOTH the hiddenEntityIds check and the frustum tests — because the saturation guard at :369 sits above them, outlineCount is bounded by what is drawn, not by the selection. A select-all whose entities are mostly off screen never ramps. This is the same fact that makes the proposed FIX 2 correct: `outlineNeeded` must be incremented AFTER the culling tests (as the fix already specifies), or the mesh grows to the selection size rather than the visible size, which is exactly the over-growth the finding criticises in the handle path at :467.

2. Only the outline path ramps. text-renderer and text-entities size from `estimatedGlyphs` (the true need) in one step, and the handle path from `selectedEntityIds.size * 8`, also one step. So the user-visible claim "all text blinks out for at least one frame per capacity step" is really one blank window per growth event, typically a single step rather than a sequence. The blank window itself is real and is two frames rather than one, because `lastEntriesRef.current = entries` is assigned at :163 BEFORE the capacity check at :169, so subsequent frames early-return on reference equality until the `useEffect([buffers])` resets the sentinel — which the finding already records under "could regress" item 3. Defect stands; the eight-frame framing applies to the outline mesh only.

### safety

FIX 1 — the rAF deferral — should not ship as written. It buys nothing and costs a frame, and the frame it costs is spent on the finding's own user-visible symptom #2.

1. React 19 does not render synchronously on a `setState` from a `useFrame` callback. The update lands at DefaultLane and is scheduled through the Scheduler's MessageChannel, so it already commits BETWEEN frames, not inside the frame callback. Wrapping the same `setState` in `requestAnimationFrame` produces the same commit and the same `<instancedMesh>` remount, one animation frame later — R3F's `loop()` re-requests its own rAF at the end, so the deferred callback runs at the head of frame N+1 and its commit still lands after that frame's paint. The dedupe guard (`newCapacity > pendingCapacityRef.current`) is a no-op here: `useFrame` runs once per frame per component, so there is at most one growth call per frame per site to collapse.

2. text-renderer.tsx:171 and text-entities.tsx:151 keep the `return;`, and the plan concedes (could-regress 3) that the blank window becomes two frames. FIX 2 does not apply to those two files, so the ONLY change the proposal makes to the text path lengthens the artefact it names ("all text blinks out for at least one frame"). What actually costs a person that frame is `return;` + `key={capacity}` remounting a mesh whose fresh `instanceMatrix` is all zeros — not which callback the setState is called from.

3. The finding already concedes FIX 1 changes no commit count ("eight deferred commits instead of eight synchronous ones"). counts.mjs measures commits, so FIX 1 moves nothing there except by spreading identical commits over twice as many frames — the per-frame number improves while the artefact lasts longer. That is fitting the instrument. Only FIX 2 reduces the count (8 → 1).

4. The repo's nearer precedent contradicts the choice of rAF: text-entities.tsx:~450 already defers out of the frame callback with `queueMicrotask` (the dimension flush), which costs zero frames. sockets.tsx's rAF was written before that and has never been measured either.

5. could-regress 2 is overstated in the direction that matters: today's ramp CONVERGES (it grows while written == capacity and stops once capacity exceeds the visible-selected count), so today's settled capacity is in (needed, 1.5·needed]. FIX 2 allocates ceil(1.5·needed) — at most ~37–50% more (1500 vs 1094 at needed=1000), not "75k vs whatever the ramp reached". FIX 2 is safer than advertised.

6. Plan inconsistencies to fix before implementing: the sites list gives entity-selection one ref pair while FIX 1's body correctly needs two (outline and handle), with the single unmount effect cancelling both; "route setHasSemiboldEntries through the same rAF" cannot be literal (different component, boolean not number); and the summary line has the two fixes swapped — FIX 2 is the one that removes the ramp, not the one that leaves it.

Recommendation: land FIX 2 alone. It fixes symptom 1 outright and reduces the commits 8 → 1 with no deferral. If FIX 1 is wanted anyway, it must come with the unmount `cancelAnimationFrame` (both pairs) AND a measured before/after on the text blank window, because as written it makes that window worse.

### minimal

FIX 2 (size from true need) is the necessary part. FIX 1 (the rAF deferral) is the bulk of the change and should not be committed, for three reasons I checked.

(1) A SIMPLER MECHANISM ALREADY EXISTS IN THIS PACKAGE, and the finding cites the wrong precedent. nodes.tsx:357-360 and reroute-nodes.tsx:191-193 both grow capacity inside the STORE SUBSCRIPTION — no rAF, no pendingCapacityRef, no unmount cleanup, no split counter. entity-selection.tsx:314-315 ALREADY subscribes to selectedEntityIds and hoveredEntityId. Both setState-in-useFrame sites in that file can be deleted by moving growth into that existing subscriber with a functional updater — `setOutlineCapacity(c => need > c ? Math.ceil(need*1.5) : c)` with `need = ids.size + 1` (the +1 is the hover slot writeOutline uses) — which needs no dependency change at all. That is smaller than FIX 1 + FIX 2 combined AND strictly better: the store update fires inside a pointer handler, so React commits before the next paint and the full outline set paints on frame one, where FIX 2 still leaves one partial frame. The memory objection ("could regress" #2, sizing by selection rather than by culled count) does not distinguish the two: the handle mesh in the same component already allocates selectedEntityIds.size * 8, i.e. 8x more, un-culled, today.

(2) FIX 1 RESTS ON A PREMISE REACT 19 MAKES FALSE. Peer deps are react >=19 / @react-three/fiber >=9. A setState from a useFrame callback is not flushed synchronously — React schedules it and commits after the frame callback returns. sockets.tsx:659's own comment ("defer state update to avoid React re-render inside useFrame") describes something that does not happen under React 19. The rAF wrapper does not move the commit off the frame path; it delays it one frame into the next inter-frame gap. Its only real yield is max-coalescing across frames, and once capacity is sized from true need there is nothing to coalesce. Copying it into three more files propagates a cargo-culted idiom rather than a mechanism.

(3) FOR TEXT IT MAKES THE STATED SYMPTOM WORSE, which the proposal itself concedes ("could regress" #3: "the blank window is now two frames rather than one"). The text path has NO RAMP — countGlyphs / countMultiLineGlyphs compute the true need, so growth is a single step to 1.5x need and capacity never shrinks in any of these components. So user-visible claim #2 is overstated: it is a small number of single-frame flickers at new high-water marks (mount, first zoom-out), not a recurring pan cost, because panning at constant zoom barely moves the visible glyph count and so does not re-trigger. text-renderer.tsx and text-entities.tsx should be left alone, or fixed at the real cause (the `return` at :171/:151 plus `key={capacity}`), not given the deferral.

Claim #1 is also softer than stated: the ramp is real but ONE-TIME PER SESSION, since capacity only ever grows — a second select-all is instant — and it needs >64 selected AND unculled entities.

Two smaller corrections. The bundling rationale is inverted: "the second alone leaves the ramp" is wrong, FIX 2 IS the ramp fix and FIX 1 alone is what leaves it. And "could regress" #1 overstates the unmount cancelAnimationFrame — since React 18 a setState after unmount is a silent no-op, so that cleanup is hygiene, not a bug guard.

The optional third item (routing setHasSemiboldEntries at text-renderer.tsx:565/:596 and text-entities.tsx:447 through the same rAF) buys literally nothing and should be dropped: the <TextWeightRenderer> mount/unmount is caused by the conditional render, not by when the state lands, so deferring it delays the same construct/destruct by one frame. If zoom-boundary thrash is the concern the answer is hysteresis or keeping the subtree mounted at count=0 — a different change needing its own judgement.

Recommended minimal commit: entity-selection.tsx only — move both capacity growths into the existing selectedEntityIds subscriber with functional updaters, and delete the two setState calls from useFrame. No new refs, no rAF, no unmount effect, no outlineNeeded counter, and no change to text-renderer.tsx or text-entities.tsx. Note that this leaves the `hiddenEntityIds` / `resizable === false` over-allocation ("could regress" #5) exactly as it is today.

One inference I could not measure (read-only): that a freshly constructed THREE.InstancedMesh arrives with count === capacity over a zeroed matrix buffer, which is what makes the remount frame blank. It bears on how severe symptom #2 is, not on the recommendation.
