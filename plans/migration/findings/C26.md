## What a person experiences

Four things, in ascending order of how visible they are.

A page with image nodes grows its memory by the full decoded size of every image it has ever shown — a 2048x2048 full-res tier is ~16MB of pixel buffer outside the JS heap — and does not give it back on delete, on LRU eviction, or on unmount. `dispose()` frees the GPU copy; the CPU-side ImageBitmap is left for non-deterministic GC.

Under a CSP that does not allow `worker-src blob:`, or in a sandboxed iframe, EVERY image entity renders as the grey placeholder forever, with a `console.warn` per image. The main-thread decode path that would have worked exists in the file and is unreachable. This is silent in development and appears only on a hardened host.

With three or more image entities zoomed past 256px of screen width at once, each one past the first two is fetched over the network and decoded at least twice, and one GPU texture per duplicate is leaked. Once the leaked count pushes `fullResCount` past 32, full-res STOPS WORKING FOR THE REST OF THE SESSION: every newly uploaded full-res texture is evicted on the frame it arrives, images stay pinned at their 256px thumbnail no matter how far you zoom in, and the manager runs a continuous fetch-decode-evict loop. On the failure path (blocked worker, 404 on the re-fetch) the same loop runs at frame rate during any pan or zoom — one `fetch()` and one `console.warn` per image per frame.

Fourth, no user sees it today but it is a device-dependent black quad: if an engine ignores `createImageBitmap`'s resize options, or a consumer passes `maxImageTextureSize` above the device's real `MAX_TEXTURE_SIZE`, an over-large bitmap is uploaded with no check and the upload fails.

## Proposed fix

Four independent edits, all in `src/utils/image-loader.ts` except one.

1. #70 — add a module-scope helper next to `bitmapToTexture` (after image-loader.ts:96):
```ts
function disposeTexture(tex: THREE.Texture | null): void {
  if (!tex) return;
  tex.dispose();
  const img = tex.image as ImageBitmap | null;
  if (img && typeof img.close === 'function') img.close();
  tex.image = null;
}
```
and route the three disposal sites through it: `release()` :212-213, `disposeAll()` :258-259, `evictFullRes()` :282. In `evictFullRes` the order is already safe (`entry.full = null` at :283 and `processUploadQueue` sets `fullDirtyRef` at image-entities.tsx:365, so the uniform is re-pointed the same frame).

2. #58 — move the state reset from enqueue to drain. Delete `entry.fullLoadState = 'idle';` at :418 (keep `entry.blob = null;` and `this.onLoad?.();`), and rewrite the full branch of `processUploadQueue` :158-161 as:
```ts
      } else {
        if (!entry.full) this.fullResCount++;
        disposeTexture(entry.full);
        entry.full = tex;
        entry.fullLoadState = 'idle';
      }
```
Do the same dispose-before-overwrite on the thumbnail branch at :157 (`disposeTexture(entry.thumbnail); entry.thumbnail = tex;`). Add `if (entry) entry.fullLoadState = 'idle';` is NOT needed on the dropped-entry branch at :149-152 — the entry is gone. Also pass the abort signal to the re-fetch at :377 (`fetch(src, { signal: entry.abort?.signal })`) so a release during a full decode cancels rather than merely being checked.

3. #71 — make the failure observable at construction time. In `image-decode-worker.ts`, add beside `getWorker()`:
```ts
  /** Force worker construction now so a CSP/sandbox SecurityError is observable
   *  here rather than as a decode rejection three layers up. */
  tryStart(): boolean {
    try { this.getWorker(); return true; } catch { return false; }
  }
```
and rewrite `getDecodeWorker()` (image-loader.ts:121-127) with a `private workerUnavailable = false;` field beside `decodeWorker` at :111:
```ts
  private getDecodeWorker(): ImageDecodeWorker | null {
    if (typeof Worker === 'undefined' || this.workerUnavailable) return null;
    if (!this.decodeWorker) {
      const w = new ImageDecodeWorker();
      if (!w.tryStart()) { this.workerUnavailable = true; return null; }
      this.decodeWorker = w;
    }
    return this.decodeWorker;
  }
```
A try/catch around `new ImageDecodeWorker()` alone does nothing — that call cannot throw. This is the smallest change that makes the existing `else` branches at :318 and :395 reachable.

4. #74 — verify the hint was honoured. In `downscale()` (:70-83), capture the result and re-check:
```ts
  const out = await createImageBitmap(bitmap, 0, 0, width, height, { resizeWidth: tw, resizeHeight: th, resizeQuality: 'medium' });
  if (out.width <= maxDim && out.height <= maxDim) return out;
  // Engine ignored the resize hint — draw through a canvas instead.
  const c = new OffscreenCanvas(tw, th);
  c.getContext('2d')!.drawImage(out, 0, 0, tw, th);
  out.close();
  return c.transferToImageBitmap();
```
and on the worker path, gate the enqueue at :389 and :312 on the same check (`if (result.bitmap.width > this.maxTextureSize) result.bitmap = await downscale(...)`). Finally clamp the budget against the device at `image-entities.tsx:236` — take `gl` from `useThree((s) => s.gl)` and pass `Math.min(maxImageTextureSize ?? DEFAULT_MAX_IMAGE_TEXTURE_SIZE, gl.capabilities.maxTextureSize)`.

## What could regress

The bitmap close is the dangerous half, and it is the one the plan already flags ("null the uniform first"). `THREE.Texture.dispose()` does not stop a material from re-uploading: if any live `ShaderMaterial` still has `u.map.value` pointing at the texture when the next render runs, three calls `texImage2D` with `texture.image`, and a closed ImageBitmap is detached — `InvalidStateError` and a black quad instead of a picture. Setting `tex.image = null` in `disposeTexture` converts that from a throw into a no-op upload, which is why it is in the helper. The three current sites happen to be covered by the frame structure (`release` is followed by `acquire`+`getTexture` returning null, so `image-entities.tsx:494` swaps in `placeholderMat`; `evictFullRes` runs inside `processUploadQueue`, which sets `fullDirtyRef` and so re-points every VISIBLE mesh's uniform the same frame) — but a culled mesh takes the `mesh.visible = false; continue;` early-out at image-entities.tsx:436-437 and never has its uniform touched, and the `DEBUG_MIP_LEVELS` path at :473-475 holds textures in `pendingColorizeRef` across a frame. Those are the two places to check.

Moving `fullLoadState` to the drain means a full-res decode now stays "loading" for the 1-2 frames the queue takes, so a genuinely failed upload (entry deleted mid-queue, :149-152) would leave the entry stuck at `'loading'` forever with no retry — that branch must reset it or the entry must be gone, which it is.

Making the main-thread fallback reachable is a real behaviour change on hosts where it currently fails: images that render as grey placeholders today will start decoding ON THE MAIN THREAD, so a first paint with several large images will jank where it previously did not paint at all. That is the correct trade but it should be stated, not discovered.

Clamping `maxImageTextureSize` against `gl.capabilities.maxTextureSize` silently lowers the resolution a consumer asked for on low-cap devices. Existing laws it breaks: none — there is no test file for this module and no harness behaviour touches images, which is why all four defects shipped.

## The law that proves it

TWO laws, because no single tier can see all four defects. The load-bearing detail is the FIXTURE SIZE: the drain is 2 per frame and runs before `getTexture` in the same frame, so a one-image or two-image fixture gives the SAME answer for a correct and a broken implementation. A law built on one image is a law about the special case wearing the general one's name. Three images is the smallest input where they diverge.

LAW A — `src/utils/image-loader.test.ts` (new, node tier). Stub `globalThis.fetch`, `globalThis.Worker`, `globalThis.createImageBitmap` and `performance.now`, each recording its calls; the bitmap stub is `{ width, height, close: vi.fn() }`. Assert only on what the stubs recorded, never on a private field.
  A1 "a full-res tier is fetched once, however long the queue is": acquire three srcs, settle, `getTexture(src, 300)` on all three, await the decodes, `processUploadQueue(2)`, `getTexture(src, 300)` on all three again, flush.   A2 "a full-res slot is written once": assert the number of `THREE.Texture` constructions with `tier: 'full'` is 3, and that `disposeAll()` leaves every minted bitmap's `close` mock called exactly once. ## What the critics said

### exists

Two refinements, neither weakening the finding.

(a) #58's permanent-stuck consequence is conditional, not automatic: evictFullRes() only runs out of candidates when the accumulated over-count exceeds the number of live full-res entries (candidates.length < toEvict). A single duplicate leaks a texture and a bitmap and over-counts by one, but does not by itself wedge the manager. What makes accumulation one-way is that release() :213 decrements once per entry regardless of how many times that entry was counted, so each over-count is permanently stranded. The "3 or more images" trigger is precise as stated (needs >2 full-tier items queued at once, since the drain is 2/frame and shared with thumbnails).

(b) #71 has an adjacent hang path the finding does not name, which strengthens it: image-decode-worker.ts:76 installs onmessage only and no onerror. A worker that constructs successfully but fails at runtime leaves every entry in `pending` unsettled forever, so load()'s and loadFull()'s awaits never resolve or reject and fullLoadState is pinned at 'loading' with no retry and no console warning at all.

### safety

The finding stands, but two of its four proposed edits are unsafe AS WRITTEN and need guards before they ship. Neither touches the core (#70 and #58 are the valuable pair and are safe).

1. Edit #74's fallback is unsafe and self-defeating. It introduces `new OffscreenCanvas(tw, th)`, `getContext('2d')!` and `transferToImageBitmap()` — none of which appear anywhere in the codebase today (`grep -rn "OffscreenCanvas|transferToImageBitmap" src/` returns nothing). That code sits in the path that exists BECAUSE an engine ignored `createImageBitmap`'s resize options, and an engine that old plausibly lacks OffscreenCanvas entirely (Safari only shipped it in 16.4). So the fallback can throw in exactly the environment it was written for, turning a device-dependent black quad into a rejected decode — a grey placeholder plus a warn, which is worse. It also uses a non-null assertion, which this repo's CLAUDE.md explicitly bans. It must be gated on `typeof OffscreenCanvas !== 'undefined'`, returning the unverified bitmap unchanged otherwise. The `gl.capabilities.maxTextureSize` clamp in the same edit is fine and is strictly an improvement (an over-cap upload is INVALID_VALUE and samples black anyway).

2. Edit #70 has one un-analyzed reachable path, and it is the `maxImageTextureSize` prop. The cleanup effect at `image-entities.tsx:258-265` is keyed `[texManager]`, and `texManager` is `useMemo(..., [maxImageTextureSize])` at :236-237 — so a RUNTIME change of that public prop runs `disposeAll()` + `materialRefs.forEach(dispose)` + `materialRefs.clear()` WITHOUT unmounting any mesh. Materials are only created in the ref callback behind `if (!materialRefs.current.has(id))` (:329), which does not re-run for a mounted mesh, so `if (mat)` at :467 is permanently false and no new texture ever reaches the quad. Today this is invisible: the ImageBitmaps are still alive, so Three re-uploads them after `dispose()` and the images keep rendering off the orphaned manager. With close + `image = null`, those quads go empty AND emit `warn('Texture marked for update but no image data found')` EVERY FRAME forever, because after dispose `textureProperties.__version !== texture.version` stays true and the guard at 11225 is re-entered on every render. That is a pre-existing bug the fix converts from silent to loud, visible and permanent. It is narrow (it needs a consumer to change the prop at runtime; a stable literal never fires it) but it is real and the finding's "could regress" section never names it. The fix should null the uniforms in that cleanup, or simply not clear `materialRefs`.

One smaller correction: the finding's claim that the main-thread fallback will "jank" a first paint is overstated. `createImageBitmap` is specified async and decodes off-thread in Chrome even when called from the main thread; the real added main-thread cost is only the OffscreenCanvas draw in edit #74, which is the edit that should be gated anyway. The genuine caution about edit #71 is different and worth stating plainly: it makes two `else` branches (:318-340, :395-414) reachable for the first time in any browser environment. I read both and they are correct — the `thumbBitmap !== bitmap` identity guards are right and the abort handling is complete — so this ships previously-dead but sound code, not previously-dead broken code.

### minimal

Three minimality objections survive and should shape the commit. FIRST, sub-item #74 is where the fix exceeds the defect and should be cut back. The finding itself concedes "no user sees it today". The proposed remedy adds an OffscreenCanvas + transferToImageBitmap re-encode inside downscale() plus re-checks on both worker enqueue sites — and that remedy depends on a NEWER platform feature than the resize-option support it defends against (transferToImageBitmap/OffscreenCanvas landed in Safari 16.4; an engine old enough to ignore resizeWidth is the one most likely to lack it), so the fallback itself needs a fallback. Keep at most the one-line device clamp at image-entities.tsx:236, and note even that only bites when a consumer passes maxImageTextureSize above the device max — DEFAULT_MAX_IMAGE_TEXTURE_SIZE is 2048, which every WebGL2 device is required to support. SECOND, one named regression risk is dead code: DEBUG_MIP_LEVELS is hard-coded `false` at image-entities.tsx:34, so the pendingColorizeRef hazard in "could regress" cannot occur and is not a place to check. THIRD, three impact statements are overstated. (a) Under a blocked worker, images render the ERROR material, not the grey placeholder — image-entities.tsx:495 reads `entry?.state === 'error' ? errorMat : placeholderMat` and load()'s catch sets state='error'; errorMat is THEME_COLORS.edge.invalid, so the symptom is a coloured quad, not a grey one. (b) The duplicate loadFull fetch is the same URL and will usually be absorbed by the HTTP cache (and is memory-backed entirely for blob: URLs from createDemoImageBlobURL) — the durable costs are the duplicate decode, the overwritten-without-dispose texture at :159 and the permanently inflated fullResCount, not bandwidth. And the failure-path loop is per round-trip, not per frame: `fullLoadState = 'loading'` at :365 blocks re-entry while a fetch is in flight. (c) The #70 memory growth is bounded by GC rather than permanent — the ImageBitmap becomes unreachable once the entry is deleted — so "does not give it back" should read "gives it back only non-deterministically, outside the JS heap". That is still the standard reason to call close(), and at ~5 lines plus three call sites the fix is proportionate; the wording just should not promise an unbounded leak.
