## What a person experiences

A screen-reader user cannot operate the graph. On a node, every socket widget announces as an unnamed control or, worse, as a *duplicated* one: three text sockets on one node all read "Enter text…, edit text" because the socket's identity ("Prompt", "Body", "Seed", "Scale") is drawn into a GL instanced mesh and never enters the DOM. The three toolbar number fields have literally no accessible name — no label, no placeholder, no title — so font size, line height and letter spacing are three indistinguishable edit boxes. Six toolbar segments announce as "radio, not selected" with no word attached, so alignment and sizing mode are unusable. The two selects announce their current value ("Regular", "System") and never their purpose. Voice-control users are hit as well: "click Font size" has nothing to match. And in text-edit mode the capture textarea — the only DOM element carrying the content being typed — is an unnamed field, with `autoComplete`/`spellCheck` unset so the browser may offer autofill over a canvas text edit.

## Proposed fix

Pure attribute additions plus one optional field on a published type. No behaviour changes anywhere.

1. `types/index.ts:62` — add to `WidgetProps`: `/** Accessible name for the control (the socket's name). */ label?: string;`. Optional, so a consumer's custom `widgetTypes` component keeps compiling.
2. `widgets-layer.tsx:93` — add `socketName: string;` to `SocketWidgetProps`; `:129` pass `label={socketName}` to `<WidgetComponent>`; `:158` add `prev.socketName === next.socketName &&` to the memo comparator; `:488` pass `socketName={socket.name}`.
3. `widgets-layer.tsx:479` — `role="group" aria-label={socket.name}`.
4. Each of the seven widget files: destructure `label` from `WidgetProps` and forward `aria-label={label}` onto the control it already renders. Verified reachable: kookie-ui spreads consumer props onto the real element in every case — `text-field.tsx:97` (`<input spellCheck="false" {...nativeInputProps} {...ariaProps} …>`, and `ariaProps` holds only `aria-invalid`/`-describedby`/`-labelledby`, so `aria-label` survives), `text-area.tsx:75-79`, `select.tsx:89`, `checkbox.tsx:47`, `segmented-control.tsx:90`. `RemovedProps = 'asChild'|'defaultChecked'|'defaultValue'|'color'`, so `aria-label` is type-legal everywhere.
5. `toolbar.tsx:480` — add `'aria-hidden': true` to `iconProps`, which retires all six bare `<svg>` in one edit.
6. `toolbar.tsx:755,758,761,820,823,826` — `aria-label="Auto width"`, `"Auto height"`, `"Fixed size"`, `"Align left"`, `"Align centre"`, `"Align right"`. `toolbar.tsx:697,815,861` — `aria-label="Sizing mode"`, `"Text alignment"`, `"Object fit"` on the three Roots (names the radiogroup).
7. `toolbar.tsx:578` — add `label: string` to `ToolbarNumberInput`'s props and forward `aria-label={label}` at `:605`; pass `label="Font size"` / `"Line height"` / `"Letter spacing"` at `:771,780,789`. Same shape for `ToolbarColorInput` (`:643`, `:655`, call site `:852` → `"Text colour"`). `toolbar.tsx:803,840` — `aria-label="Font weight"` / `"Font family"`.
8. `text-edit-overlay.tsx:382` — `aria-label="Text content"`, `autoComplete="off"`, `autoCorrect="off"`, `autoCapitalize="off"`, `spellCheck={false}`.

THREE things this fix must NOT do, each of which looks like part of the same job:

- **Do not `aria-hidden` the capture textarea.** The audit's #125 wording says "unhidden from AT", but `text-edit-overlay.tsx:94` calls `ta.focus()` and the element holds the live content. `aria-hidden` on a focused element is the `aria-hidden-focus` violation and would take text editing away from AT users entirely rather than fixing anything. Name it; leave it exposed.
- **Do not add `role="toolbar"`** to the container at `toolbar.tsx:359-368`. APG's toolbar pattern obliges a roving tabindex that this component does not implement, so the role would make the keyboard story worse. That is a separate, non-additive decision.
- **`aria-label` cannot name the slider, and no amount of care in this repo changes that.** kookie-ui hardcodes the name on each thumb — `slider.tsx:190-196`: `<SliderPrimitive.Thumb … aria-label={isRange ? … : \`Slider value: ${unit ? \`${value} ${unit}\` : value}\`} />` — and the thumb is the `role="slider"` element. A consumer `aria-label` lands on `SliderPrimitive.Root` (`slider.tsx:181`), a `<span>` carrying no slider role. So a `Scale` socket will still announce "Slider value: 0.5, slider"; its only identity is the wrapper group's name from step 3. State this in the commit rather than letting a per-widget law fail on correct code — the real repair is upstream in kookie-ui.

Adjacent, found while confirming and outside C27's scope: `BUILTIN_DEFAULTS.comment` lists `'backgroundColor'` (toolbar.tsx:109) and `BuiltInWidget`'s switch has no `case 'backgroundColor'`, so it falls to `default: return null` (toolbar.tsx:871-872) — a comment's background-colour control silently does not exist.

## What could regress

Nothing observable — these are additions to elements that today contribute no name. The three real hazards are in the *fix*, not in what it changes:

1. **The memo comparator at `widgets-layer.tsx:155-168`.** `SocketWidget` is `memo`'d with a hand-written comparator listing every prop by name. Adding `socketName` to `SocketWidgetProps` without adding `prev.socketName === next.socketName` at `:158` means a socket renamed through the controlled-component path keeps announcing its OLD name for the life of the mount — a stale accessible name is worse than an absent one, because nothing looks broken. No existing law can see it: `grep -rn "aria" harness/ src/**/*.test.*` returns zero a11y assertions anywhere in the repo, and the only `.dom.test.ts` is `color.dom.test.ts`.

2. **`WidgetProps` is a published type** (`types/index.ts:62`, reached from the public `widgetTypes?: Record<string, React.ComponentType<WidgetProps>>` at `:870`). The field must be OPTIONAL or every consumer's custom widget stops compiling. `label?: string` is source-compatible in both directions.

3. **The naming must not collide with what kookie-ui already writes.** `TextArea` and `TextField` build an `ariaProps` object spread AFTER the consumer's props (`text-area.tsx:79`, `text-field.tsx:97`), but it contains only `aria-invalid`/`aria-describedby`/`aria-labelledby` — checked, `aria-label` is not in it. `Slider` is the one that does collide, per the caveat above.

The existing laws that could catch a mistake here: none. The 196 unit laws are node-tier graph/store/colour maths, and the 37 behaviours in `harness/behaviors.mjs` drive pointer and keyboard input with no ARIA assertion in the file (`grep -n "aria" harness/behaviors.mjs` → nothing). So this commit is entirely uncovered until its own law lands, which is the argument for writing the law first.

## The law that proves it

**Primary law — `harness/spikes/a11y-names.mjs`, reading Chrome's own accessibility tree over CDP.** The standing rule bites hard here: `el.getAttribute('aria-label')` is a DECLARED value and is exactly one indirection short — it cannot see an `aria-label` that loses to an `aria-labelledby`, one placed on a wrapper that never becomes the control's name (the Slider case), or one on an element the culling has taken out of the tree. So the law reads the browser's computed output: `page.context().newCDPSession(page)` → `Accessibility.enable` → `Accessibility.getFullAXTree`, and asserts on `AXNode.name.value`, which is the string a screen reader receives.

Structure, in order:

1. Load the fixture at `?shapes=1&widgets=1`, at a zoom above `minWidgetZoom` (default 0.1; `widgets-layer.tsx:289` sets the whole container `visibility: hidden` below it, and `visibility: hidden` removes a subtree from the AX tree entirely).
2. **Vacuity guard, asserted before anything else.** Count the AX nodes whose role is one of `textbox|combobox|checkbox|slider|group` that descend from the widgets container, and require ≥ 8. Zero widgets is an ERROR, never a pass — this repo has already shipped a spike that reported zero for every interaction and read like a green run (`counts.mjs`'s dead React counter, recorded in `audit-findings.md`).
3. **The per-control assertion.** For each visible `[data-entity-id][data-socket-index]` wrapper, read the socket's `name` out of `__harness` store state, then assert Chrome's computed name on the innermost focusable control equals it.
4. **The general-case half, and the reason the fixture is the right one.** Assert the multiset of computed names EQUALS the multiset of socket names for the mounted shapes. `harness/fixture/graph.ts` already carries `Prompt`/`Scale` (`:167-168`), `Body`/`Seed` (`:179-180`), `Tall`/`Normal` (`:191-192`), `Top`/`Bottom` (`:203-204`) — distinct names across distinct widget types (text, slider, textarea-with-rows, number). A fixture of identically-named sockets would agree with a correct implementation AND with one that hardcodes a single string; this one does not.

**The sabotages, each of which must fail a DIFFERENT assertion:**

- **S1 — presence.** Delete `aria-label={label}` from `TextWidget.tsx:26` only. The `Prompt` socket's textbox computes `name.value === ""`. Step 3 must fail naming that socket. (A law that only ran step 4 as a set-comparison would also fail, but less legibly — both should be present.)
- **S2 — THE one that separates a naming law from an attribute-presence law.** Replace `label={socketName}` at `widgets-layer.tsx:129` with a constant `label="Value"`. Every control now has a non-empty, present, correctly-placed `aria-label`; a law asserting "each control has some name" PASSES. Step 4 must fail with `["Value","Value","Value",…] ≠ ["Prompt","Scale","Body","Seed",…]`. If step 4 is missing, the law is about attributes existing, not about controls being named, and it is wearing the general case's name.
- **S3 — the memo trap.** With the fix in, drive `__harness` to rename `stacked`'s `in-0` from `Prompt` to `Renamed` and assert the computed name follows. Then remove `prev.socketName === next.socketName` from `widgets-layer.tsx:158`. The control must keep announcing `Prompt` and the law must fail. Without this assertion the fix ships a stale-name bug that nothing can see.
- **S4 — the instrument's own vacuity.** Run the law at zoom 0.05 (below `minWidgetZoom`), where `widgets-layer.tsx:289` hides the container. The law must report `0 widget nodes found → ERROR`, not a pass. If it passes, it is measuring nothing and every other sabotage above is meaningless.
- **S5 — the toolbar half.** With a text entity selected and the toolbar visible, delete `aria-label` from `toolbar.tsx:820`. Chrome must report a node with `role: 'radio'` and `name.value === ""` inside the `radiogroup`, and the law must fail. Its own vacuity guard: assert exactly 6 `radio` nodes and 6 named non-radio controls first, because `toolbar.tsx:355-356` returns an empty `<div>` when `!visible` and a law that found no controls would otherwise pass silently.

**S5 has a prerequisite that is real work, and it should be priced before the commit is planned.** The toolbar is currently unmeasurable in the harness for two independent reasons: `harness/fixture/app.tsx:492-501` places `<Probe />` inside `<KookieFlow>` and never a `<Toolbar />`; and every entity in `harness/fixture/graph.ts` is `type: 'default'` (`grep -c "type: 'text'"` → 0), while `BUILTIN_DEFAULTS` (toolbar.tsx:107-110) is keyed on `text`/`image`/`comment`, so `resolveToolbarContent` returns null at `toolbar.tsx:427` and no built-in widget ever renders. The fixture needs one text entity plus a `<Toolbar />` and a selection. This is the same gap `audit-findings.md` already records for fix 17 ("the harness never mounts the component the toolbar loop lived in") — closing it here pays for that too.

**Cheap tier, as a fast gate rather than the proof:** a `src/components/widgets-layer.dom.test.tsx` using the already-installed `@testing-library/react` with `getByRole('textbox', { name: 'Prompt' })`. Its `name` filter runs `dom-accessibility-api`'s `computeAccessibleName` (present at `node_modules/.pnpm/dom-accessibility-api@0.5.16`), so it is still a computed read rather than an attribute read — but it is a JavaScript reimplementation of accname in jsdom, not Chrome's own tree, so it belongs in the `dom` vitest project as the fast gate while the CDP law carries the proof.

## What the critics said

### exists

Two factual errors in the finding's reasoning, neither of which rescues the code, but both of which would poison a law written from the finding's text:

1. The finding states SegmentedControl.Root is `role="radiogroup"`. It is not. At the pinned @radix-ui/react-toggle-group@1.1.11, ToggleGroupImpl sets `const commonProps = { role: "group", dir: direction, ...toggleGroupProps }` unconditionally, independent of `type`; only the Item gets `const singleProps = { role: "radio", "aria-checked": props.pressed, "aria-pressed": void 0 }`. kookie-ui passes no role in rootProps, so the Root renders role="group". The six unnamed role="radio" controls are real and the defect stands, but a law asserting role="radiogroup" on the Root would fail against correct code. (It also means six role="radio" elements sit inside a plain group rather than a radiogroup — a separate structural issue outside C27's scope.)

2. The finding quotes kookie-ui segmented-control.tsx:95-97 as a single `<span className="rt-SegmentedControlItemLabel">{children}</span>`. The real source renders children TWICE — an active span plus an `aria-hidden` inactive span. The conclusion is unchanged (the name still comes from children, and a bare <svg> contributes nothing), but it makes proposed fix step 6 load-bearing rather than belt-and-braces: adding 'aria-hidden' to iconProps empties BOTH spans, so the per-Item aria-label is the only thing that can supply a name.

### safety

Three things in the proposal are overstated or worth changing, none of them fatal:

(a) "No behaviour changes anywhere" is not true of step 8. `aria-label`, `autoComplete="off"` and `spellCheck={false}` on the capture textarea are inert (the element is 1px at `opacity: 0`), but `autoCorrect="off"` and `autoCapitalize="off"` are a real input-behaviour change on touch devices: soft keyboards stop auto-capitalising sentences and iOS stops autocorrecting into a field whose `onInput` mirrors straight into the GL text entity. I think that is the right call — autocorrect silently rewriting canvas text is worse than the alternative — but it is a behaviour change, so it belongs in the commit message rather than under a blanket "pure attribute additions". If the commit wants to be strictly non-behavioural, ship the name and drop those two.

(b) Name the published field something other than `label`. `WidgetProps` is public (`widgetTypes?: Record<string, React.ComponentType<WidgetProps>>`), and `label` is a React-known DOM attribute, so any consumer widget that spreads `{...props}` onto an element will silently render `label="Prompt"` in the DOM, and any consumer already using `label` as their own prop name receives a value they did not pass. `ariaLabel?: string` or `socketName?: string` has the same optionality and no attribute collision.

(c) The plan's own claim that step 2 changes nothing about rendering is only true because the comparator term is added. Left off, the failure is the stale-name one the plan already describes; added, `SocketWidget` re-renders on rename, which I verified is safe (state initialiser does not re-run) — worth stating, since "makes a memo stricter" is normally the thing this repo's performance rules ask you to justify.

### minimal

Three notes for the commit, none refuting the fix. (a) Step 3's aria-label on the role="group" wrapper is redundant with step 4 for six of seven widget types (a user hears "Prompt, group / Prompt, edit text"); keep it, but for the stated reason — it is the ONLY name a slider socket can get, given the hardcoded thumb label. (b) label?: string on WidgetProps is necessary rather than convenience: the wrapper cannot reach inside a consumer's custom widgetTypes component, so it is the only route by which a third-party widget can be named. (c) Found at the exact call site the fix edits: `disabled` is NEVER passed to <WidgetComponent> at widgets-layer.tsx:129-139 (grep -n disabled src/components/widgets-layer.tsx returns nothing), yet all seven built-ins destructure and use it — so connected sockets render live, editable widgets. Out of C27's scope, but unavoidable to notice when adding label={socketName} to that prop list. The adjacent backgroundColor note also confirmed: BuiltInWidget's switch has ten cases, none 'backgroundColor', while BUILTIN_DEFAULTS.comment (toolbar.tsx:109) requests it, so it falls to `default: return null`.
