## What a person experiences

Three things, and only one of them is "slow".

1. A collapsed group leaves its children's socket dots painted over the frame, and they are not pressable. core/store.ts:428 keeps hidden entities out of the socket quadtree while sockets.tsx:636 draws them, so the paint and the hit test already disagree. On the existing `scene=group` fixture that is 4 dots (child-a and child-b, in and out) sitting on a collapsed frame that a press goes straight through. Edges do the same: `ge0` (child-a → child-b, both hidden) is still drawn inside the collapsed frame.

2. Every socket in the document is submitted to the GPU twice, every frame, whatever is on screen. Measured 24,172 instances/frame at 2,000 entities against ~2,893 at 200 — an 8.5x rise on a viewport showing roughly the same twenty nodes. At the 50k-node scale in the migration brief that is ~600k instances per frame.

3. Every edge is submitted twice, every frame, at full tessellation. VERTICES_PER_EDGE is `64 * 6 + 6 = 390` (edges.tsx:18-21), and the fixture makes 0.8 edges per entity, so 2,000 entities is 1,600 edges = 624,000 vertices, doubled by the bg/fg mesh pair = ~1.25M vertices per frame with the vertex shader doing the discarding (edges.tsx:64-67 throws away off-layer vertices by writing `gl_Position = vec4(2.0,...)`).

Note what is NOT user-visible and must not be claimed as a win: hit testing is untouched by this. `getEdgeAtPosition` (utils/geometry.ts:578) walks the `edges` array and `getSocketAtPositionFast` (utils/geometry.ts:317) goes through the quadtree; neither reads the render buffers.

## Proposed fix

Two commits, in this order. The audit is right that inverting them makes geometry vanish while panning, and the ordering is not a style preference: with no viewport subscription, a cull is evaluated once and then never re-evaluated as the camera moves.

COMMIT 1 — invalidation only, no cull, measure it.
sockets.tsx: at line 324, replace the "viewport changes no longer trigger dirty" comment with two subscriptions in nodes.tsx:363-370's exact shape — `store.subscribe((s) => s.viewport, () => { dirtyRef.current = true; })` and the same for `s.hiddenEntityIds` — and add both to the cleanup at 371-376.
edges.tsx: the same two subscriptions after `unsubPositions` (line 373), each setting `geometryDirtyRef.current = true`, added to the cleanup at 408-414.
Ship nothing else. `setViewport` is called per pointermove and is deliberately not rAF-batched (kookie-flow.tsx:667-674), so the dirty flag is what collapses the events into one rebuild per frame. Run counts.mjs at 200 and 2000 BEFORE the cull: this commit is a pure cost — edges do zero CPU work during pan today, and this makes them re-tessellate 1,600 edges per pan frame. If the allocation/frame column moves badly here, commit 2 has to carry a hysteresis (rebuild only when the viewport has moved more than the cull padding since the last rebuild) rather than nodes.tsx's unconditional dirty.

COMMIT 2a — sockets.
Read `viewport` and `hiddenEntityIds` in the destructure at sockets.tsx:600. Compute the four bounds exactly as nodes.tsx:411-416 does (`size` is already the useFrame parameter at 509). Hoist `const entityLayout = getEntitySocketLayout(entity, socketLayout);` out of `writeEntitySockets` (sockets.tsx:399) into the loop at 636 and pass it in as a parameter, so the cull test and the write share the one cache lookup the existing comment at 396-398 exists to protect. In the loop at 636, before calling `writeEntitySockets`:
  - `if (hiddenEntityIds.has(entity.id)) { socketRanges.set(entity.id, { mesh: 'bg', start: totalCount, count: 0 }); continue; }`
  - bounds: left = `getSocketWorldX(entity, true)`, right = `getSocketWorldX(entity, false)`, top = `entity.position.y`, bottom = `entity.position.y + (entity.height ?? entityLayout.computedHeight)`. Use those two helpers rather than naming SOCKET_OFFSET — `src/socket-geometry-home.test.ts:58-66` fails any file outside utils/geometry.ts that mentions it, and the helpers give the true painted extent for free.
  - four-comparison test with a padding, same `continue` + zero-count record.
Then guard the position fast path at sockets.tsx:530-541: `const range = socketRanges.get(entityId); if (!range) continue; if (range.count === 0) { dirtyRef.current = true; continue; }` — and after the `for (const entityId of movedIds)` loop, if `dirtyRef.current` was set, do NOT `return` at 574; fall through to the full rebuild this frame. Without that escalation, dragging a culled entity into view leaves it invisible; without the `count === 0` check, it writes 6 matrices over whichever neighbour legitimately owns `[range.start, range.start + 6)`.

COMMIT 2b — edges.
Read `hiddenEntityIds` at edges.tsx:422; compute the same four bounds. Turn `const isPartialUpdate` (edges.tsx:555) into a `let`, and while building `affectedEdgeIndices` (edges.tsx:580-594) set `isPartialUpdate = false` if any affected index has `evCounts[i] === 0` — escalating there rather than mid-loop avoids fighting the unconditional flag clearing at 1207-1210. Put the cull immediately after `cy2 = y1;` (edges.tsx:722), where all eight control-point coordinates are in scope: a cubic bezier lies inside the convex hull of its control points, so `min/max(x0, x1, cx1, cx2)` and `min/max(y0, y1, cy1, cy2)` is an exact bound, which is what the comment at 683 was always describing. On a cull, mirror the existing zero-count record at 613-617 — `evStarts[i] = vertexIndex; evCounts[i] = 0;` — and also set `edgeLayers[i]` so the layer fast path at 480-495 does not hold a stale value across the culled window. Delete/rewrite the comments at 680 and 683.
The hidden half for edges is the sign-off half and should be `hiddenEntityIds.has(edge.source) && hiddenEntityIds.has(edge.target)` — BOTH, not either. Skipping on either endpoint erases every edge crossing a collapse boundary (`ge1` in harness/fixture/graph.ts:284, which exists for exactly this question) and there is no proxy/reroute logic to replace it with.

Padding: it must exceed the ribbon's world half-width `EDGE_WIDTH / 2 / zoom` (edges.tsx:26, expanded in the shader at 76-78) plus `ARROW_HEIGHT` = 12 (edges.tsx:32). MIN_ZOOM is 0.01 (core/constants.ts:16), so a constant like nodes.tsx's 300 is not automatically safe — derive it as `Math.max(300, (EDGE_WIDTH + ARROW_HEIGHT * 2) / viewport.zoom)`.

## What could regress

1. THE TRAMPLE. Both fast paths index by a recorded start and never read the recorded count — sockets.tsx:541 `let instanceIdx = range.start;` then writes `inputs.length + outputs.length` matrices, and edges.tsx:606 `vertexIndex = evStarts[i];` then writes up to 390 vertices. Today no range is ever zero-count for a live entity, so the hazard does not exist; culling creates it. A culled entity that is then dragged overwrites its neighbour's instances. Auto-scroll (kookie-flow.tsx:713 `setViewport` inside the drag loop) is the path that produces this without any deliberate effort, and note it is currently dead from C23's stale `isDragging` closure — so C17 and C23 arm each other. NO EXISTING LAW CATCHES THIS: there are no renderer tests in src (`find . -name '*.test.ts*'` gives ten files, all store/geometry/text), and behaviors.mjs has nothing that drags an off-screen entity.

2. DRAGGED INTO VIEW, NEVER APPEARS. A position change does not invalidate a cull decision. Without the escalation in the fast path, a culled entity dragged on-screen stays invisible until some unrelated event marks the renderer dirty.

3. THE INVALIDATION IS A COST BEFORE IT IS A SAVING, for edges specifically. Today edges do ZERO CPU work during a pan — the frame function reaches the `if (!geometryDirty && !positionDirty && !colorDirty && !layerDirty) return;` at edges.tsx:440 and stops. Commit 1 turns that into a full re-tessellation of every edge on every pan and zoom frame. Commit 2 makes each rebuild cheaper but far more frequent. This is the one place the fix can be a net loss, which is why it is measured between the two commits and not after.

4. BOUNDARY-CROSSING EDGES. Culling an edge whose *either* endpoint is hidden deletes every connection between a collapsed frame and the rest of the graph. The `group` fixture's `ge1` is that case. Sign-off.

5. THE LAYER CACHE (the fix landed as audit finding 11 / 90bbf5a). `edgeLayersRef` is a per-edge cache the selection fast path compares against (edges.tsx:483). If a cull `continue`s past the layer write at 1123-1129, the cached value goes stale for the culled window. Harmless only because a full rebuild rewrites it; state it and write it on the cull path anyway.

6. `ensureCapacity` (edges.tsx:250-305) copies `buffers.lastVertexCount` worth of data, and `lastVertexCount` is set to the post-cull `vertexIndex` at 1205 — so a grow while many edges are culled copies less. Benign (a grow only happens on a full rebuild, which rewrites everything) but it is the kind of thing that looks like a bug in six months, so it wants a comment.

7. WHAT DOES NOT REGRESS, and should be said so nobody defensively "fixes" it: hit testing. `getEdgeAtPosition` (utils/geometry.ts:578) iterates the `edges` array and `getSocketAtPositionFast` (utils/geometry.ts:317) queries the socket quadtree, which core/store.ts:428 already builds from visible entities only. Culling is render-only, and for the hidden half it makes the paint AGREE with a hit test that has been right all along.

8. INSTRUMENT REGRESSION, and this one is subtle. `harness/fixture/app.tsx:257-274` walks `pos.count` — the whole attribute, capacity included — not `geometry.drawRange`. The bezier-endpoint law at behaviors.mjs:588-639 takes the NEAREST drawn vertex to each socket, so after culling it will happily find a culled edge's stale vertices sitting in the buffer past the draw range and report the edge as drawn. That law survives today only because it widens the viewport to 2700 (behaviors.mjs:589) so nothing culls — a premise that is currently true by accident and becomes load-bearing the moment C17 lands. `drawnVertices` must be clamped to `drawRange` in the same commit, or that law goes quietly vacuous.

## The law that proves it

FOUR laws. The first is the one the audit means by "T-count"; the other three exist because a count cannot see geometry vanishing.

LAW A — instances track the viewport, not the graph (harness/spikes/counts.mjs).
Run pan at `--count=200` and `--count=2000` in the SAME 1280x800 viewport and assert `instancesPerFrame` at 2000 is within a small factor of the figure at 200. This is the general-vs-special-case rule doing real work: at ONE graph size, "tracks the viewport" and "tracks the whole graph" are the same number, so a single-count law is a law about that count wearing the general one's name. Today the two readings are 2,893 and 24,172. Add a second half that computes the expectation independently from the store — `entities.filter(intersects viewport ± pad).reduce(sockets) * 2` — rather than hardcoding a number, so the law is about the mechanism and not about seed 1.
SABOTAGE THAT MUST MAKE IT FAIL: delete the four-comparison frustum test from the loop at sockets.tsx:636 (equivalently, set the cull padding to `Infinity`). The law must go red at the 24,172-class number.
VACUITY GUARD: pan to an empty region of the grid and require instances/frame to fall to the non-socket floor. A cull that is present but wired to a stale viewport passes the two-count comparison and fails this.
PREREQUISITE for the edges half: extend the existing hooks at harness/fixture/app.tsx:158-159 to accumulate a vertex count (`drawArrays(mode, first, count)` → `a[2]`; `drawElements(mode, count, ...)` → `a[1]`). Edges are non-indexed and go through `drawArrays`, so `verticesDrawn / frames` is exactly `2 * drawRange.count`. Without this the edges half of C17 has no instrument at all — reading `geometry.drawRange` instead would be reading a declared value one indirection short of what the driver was asked to draw.

LAW B — nothing that should be on screen is missing (harness/behaviors.mjs).
Pan a wide graph across its extent; at each stop, scan the framebuffer for socket-coloured blobs (the scanner at behaviors.mjs:468-540 already exists) and require at least one blob per socket the store says is inside the viewport.
SABOTAGE THAT MUST MAKE IT FAIL: cull on the entity's ORIGIN rather than its box — `entity.position.x > viewRight` in place of `entityRight < viewLeft` — which silently drops the sockets of every entity straddling the left edge. This sabotage is chosen deliberately: an off-by-one-side cull is what a correct-looking implementation actually gets wrong, and a law that only checks the middle of the viewport passes it.

LAW C — a culled entity's neighbour keeps its sockets (browser, pixel).
The law that cannot exist today, because no range is ever zero-count. Two entities A and B adjacent in `entities` order; pan so A is off-screen and B is on; drag A; assert B's socket dots are still painted at B's socket positions.
SABOTAGE THAT MUST MAKE IT FAIL: remove `if (range.count === 0) { dirtyRef.current = true; continue; }` from sockets.tsx:530-541. B's dots must move or disappear. Second sabotage, same law: remove the escalation and drag A back INTO view — A's dots must fail to appear.

LAW D — a collapsed group paints no sockets (browser, `scene=group`).
`collapseGroup('frame')` (core/store.ts:1469 — it does not require `type === 'frame'`, which `toggleGroupCollapse` at 1453-1456 does, so the fixture's `type: 'default'` frame works), then assert no socket-coloured dot lands inside the frame's rectangle, and that `outside`'s dots are still there.
SABOTAGE THAT MUST MAKE IT FAIL: remove `if (hiddenEntityIds.has(entity.id)) continue;` from the sockets loop. 4 dots reappear.
VACUITY GUARD, and it is the one that matters most: assert the scanner finds child-a's and child-b's dots BEFORE the collapse. "No dots inside the rectangle" passes perfectly on a scanner that finds nothing — the harness has already been bitten by this once, which is why behaviors.mjs:541 carries `INSTRUMENT: the scan finds a socket-coloured dot for every socket`.

Every one of these reads the browser's output — instance counts off the patched GL entry points, blobs off the framebuffer. None reads a token name, a dirty flag, or a reconstruction of the cull arithmetic; a law that recomputed the bounds from `viewport` and `size` and compared them against the renderer's would agree with a wrong implementation by construction, which is the trap that ate the first socket-geometry law (audit-findings.md, "That unification broke the first law written for it").

## What the critics said

### exists

No correction needed on the existence claim — every site, line number and quoted string in the finding matches the current source. One nuance worth carrying into the fix rather than a correction: the sockets.tsx:325 comment's "GPU handles clipping efficiently" is not wholly vacuous — the edge vertex shader at 63-67 does discard off-layer vertices, and both mesh pairs rely on that for the bg/fg split. It is layer filtering, not viewport culling, and it occurs after full CPU tessellation and submission, so it neither refutes the finding nor is it something the cull may disturb (the proposed fix's requirement to keep writing `edgeLayers[i]` on the cull path is the right instinct for exactly this reason).

### safety

The defect (C17) stands: neither edges.tsx nor sockets.tsx culls, the two comments at edges.tsx:680/683 do claim an optimisation the file lacks, and the collapsed-group socket paint genuinely disagrees with the hit test. What the finding gets wrong is the fix's safety and its cost model. Specifically: (a) "commit 2 makes each rebuild cheaper" is false for the two dominant terms on the edges side — the whole-array bufferSubData upload and the per-frame reverse-index reallocation are gated on !isPartialUpdate, so culling leaves both at full cost on every pan frame; (b) the "could regress" list omits the socket capacity policy entirely, which is the one place the fix breaks the project's stated #1 rule (React commits and InstancedMesh reconstruction mid-zoom, plus a frame of clamped/missing sockets at each growth step) — nodes.tsx is safe only because it sizes capacity from entities.length in a subscription rather than from the culled write count; (c) the proposed measurement gate ("the allocation/frame column") cannot resolve either cost, since counts.mjs records no upload bytes and its allocation column is already documented on this branch as too noisy to answer; (d) the escalation is one-directional — an edge becoming newly culled during a partial update leaves a stale ribbon inside drawRange with a zeroed layout record.

### minimal

The finding is right; the FIX is not minimal, and one part of it is structurally unable to do what the plan claims.

1. COMMIT 2 CANNOT RECOVER COMMIT 1'S DOMINANT COST, so "measure between the two commits" is not the safety valve it is presented as. `isPartialUpdate = positionDirty && !geometryDirty` (edges.tsx:555), so a viewport subscription that sets `geometryDirtyRef` makes every pan frame a FULL rebuild, and the full-rebuild upload path (edges.tsx:1190-1198) sets `needsUpdate` with NO `addUpdateRange` — which is `bufferSubData` of the entire attribute, not the draw range. The arrays are capacity-sized: `ensureCapacity(1600)` allocates ceil(1600*1.5)=2400 edges x 390 verts = 936,000 vertices, i.e. positions 11.2MB + uvs 7.5 + colors 11.2 + perp 7.5 + layers 3.7 = ~41MB re-uploaded per pan frame at the 2,000-entity fixture (~2.5 GB/s at 60fps). Culling changes `vertexIndex` and `drawRange`; it does not shrink that upload by one byte. Sockets have the same shape at smaller scale (`markSocketBuffersForUpload` + `instanceMatrix.needsUpdate`, ~1.7MB/frame, also capacity-sized). So the fix as sequenced trades a GPU cost that is very likely free for a transfer cost that is certainly not, and needs a third piece — range-limited full uploads, or the hysteresis the plan mentions only as a contingency — landing WITH or BEFORE the cull, not after it.

2. THE PERF NEED IS UNMEASURED, and this repo has already declined a change on exactly that basis. audit-findings.md T3 says in its own words "Still missing: the frame-time baseline at 1k/10k/50k". Instances/frame is not time. 24,172 socket instances is ~145k vertices/frame of a quad shader — nothing. The edges' ~1.25M verts/frame is the only figure with plausible weight, and off-screen geometry is clipped after the vertex stage essentially for free, so the entire saving is vertex-shader invocations and attribute fetches. `events={null}` was declined in the same document for buying "something below the noise floor" while disabling a subsystem; C17's viewport half is that trade with a bigger hazard attached (the trample, the escalation, the `drawnVertices` instrument change that keeps behaviors.mjs:588-639 from going vacuous).

3. THE TWO HALVES ARE SEPARABLE AND ONLY ONE HAS DEMONSTRATED IMPACT. User-visible item 1 (painted, unpressable sockets and edges inside a collapsed frame) is fixed by: subscribe to `hiddenEntityIds` in both files, `continue` on hidden (edges: BOTH endpoints), record the zero-count range, and guard the socket fast path on `range.count === 0`. `hiddenEntityIds` changes only on collapse/expand, so there is no per-frame cost, no full-rebuild-on-pan, no padding derivation, no `drawnVertices` clamp (nothing viewport-culls, so the bezier law's 2700-wide premise is untouched), and no dragged-into-view class of bug beyond the one guard. That is roughly a dozen lines and it is the half a person can see today. Items 2 and 3 are the 50k-node target, and should be filed as such.

4. IT REPEATS A MISTAKE THIS PACKAGE ALREADY PAID FOR. The plan says "compute the four bounds exactly as nodes.tsx:411-416 does" — that is copies nine and ten of the same arithmetic, which already exists in nodes, entity-selection (twice), image-entities, widgets-layer, reroute-nodes, text-renderer, text-entities and dom-layer, carrying FIVE different paddings (50/100/150/300, plus the proposed derived one). Fixes 12/13 collapsed five copies of the socket arithmetic and installed `socket-geometry-home.test.ts` to stop a sixth, on the finding that three of five copies were wrong. A cull that disagrees with `nodes.tsx`'s 300 is a node drawn without its sockets, or sockets without their node; the proposed `Math.max(300, (EDGE_WIDTH + ARROW_HEIGHT*2)/zoom)` guarantees they disagree at low zoom. If the viewport half lands at all, the bounds test belongs in one shared helper with one padding rule, not two more inline copies.
