# C34 — a theme flip leaks about 16 GL buffers, and it is not a material leak

Found by building C25's law, not by the audit. Filed rather than fixed, with the measurement, so
the next person starts from a number.

## The measurement

`harness/behaviors.mjs`, section `GPU teardown`, prints it on every run:

```
  measured  materials disposed +88, geometries +0
  measured  programs +0, buffers 122 -> 250 (+128)
```

Eight theme flips (four light→dark→light round trips, after a warm-up round trip), 12 entities.
128 GL buffers created and never deleted — about 16 per flip.

**The number is IDENTICAL with all 23 of C25's dispose effects present and with all of them
deleted.** Both runs: `122 -> 250`. So this is not a material leak and not a geometry leak, and
C25's fix does not touch it. What DOES move between those two runs is the disposal count, 8
against 88 — which is how the two were told apart.

## What it is not

**Not programs.** `createProgram` fires zero times across the eight flips in both runs. Every
`ShaderMaterial` of a kind in this package has a byte-identical shader body, so three's program
cache hands back the same program however many materials are built. This is also why C25's first
law could not fail: it asserted that eight flips leak no programs, which is true of the fixed code
AND of the code with every dispose effect deleted.

**Not the geometries.** Zero geometry disposals in both runs, because the geometries are
`[]`-memoised and a theme flip never rebuilds one.

## The likely cause, stated as a hypothesis

Every instanced mesh in the package is `<instancedMesh args={[geometry, material, capacity]}>`. A
theme flip rebuilds the material memo, which changes `args`, and R3F reconstructs a component whose
`args` change. A fresh `InstancedMesh` mints a fresh `instanceMatrix` — one GL buffer — and each
init effect then builds fresh `InstancedBufferAttribute`s, which are more. Nothing frees the old
mesh's, because the old mesh is gone and its attributes were never disposed.

Roughly 16 per flip is the right order for that: the package mounts about half a dozen instanced
meshes and each carries an instance matrix plus two to four instanced attributes.

**This is a hypothesis, not a verified cause.** It was not confirmed, because confirming it means
changing the thing described below.

## Why it is not fixed here

The obvious repair is to keep the material out of `args` — `args={[geometry, undefined, capacity]}`
with `material={material}` as a prop — so a theme flip re-points the material without
reconstructing the mesh.

That changes when the buffer-init callback ref re-runs, and **that callback ref is commit
eaaed92's fix** ("make a theme change reach WebGL, and survive being reached"). The mesh being
reconstructed is currently part of how a theme change reaches the GPU at all. Undoing the
reconstruction without re-breaking that is a real piece of work with its own laws, and folding it
into a commit about disposing materials would put the two on the same bisect step.

## What guards it meanwhile

`the known per-flip buffer leak does not get worse` — a CEILING at 20 buffers per flip, which
today's ~16 passes. Deliberately not zero: a law asserting a number the code cannot meet is a red
line nobody can act on, and it would have to be disabled the moment it landed. As a ceiling it
still catches a regression that doubles it.
