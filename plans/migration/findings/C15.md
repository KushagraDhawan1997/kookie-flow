# C15 — risk low, proof counts-spike, depends on nothing

## Is it still there

Not in the fixed table of plans/migration/audit-findings.md (fixes 1-17 close C16's layer cache, C20's dead mechanisms, the theme/geometry work — none touch this). Confirmed live in the current tree, and there are TWO leaks, not the one the audit filed.

(a) THE UNCONDITIONAL HALF, which the audit does not name. sockets.tsx:333-338 subscribes to the whole draft object:
    const unsubConnectionDraft = store.subscribe(
      (state) => state.connectionDraft,
      () => { dirtyRef.current = true; }
    );
and core/store.ts:644-655 allocates a fresh object every call:
    updateConnectionDraft: (mouseWorld, isValid) => {
      const { connectionDraft } = get();
      if (connectionDraft) { set({ connectionDraft: { ...connectionDraft, mouseWorld, isValid: isValid ?? connectionDraft.isValid } }); }
    },
called unconditionally on every pointermove at kookie-flow.tsx:1206: `store.getState().updateConnectionDraft(worldPos, isTypeCompatible);`. subscribeWithSelector compares with Object.is, so a new identity every move sets the COARSE dirtyRef every frame — regardless of what is under the pointer. sockets.tsx never reads mouseWorld or isValid; its own parameter type at :391 declares only `connectionDraft: { source: {...} } | null`, and grep confirms the only reads are `.source.*` (:434, :435, :486, :487, :609, :613, :615, :619) and truthiness (:446, :498, :608).

(b) THE HOVERED HALF, which the audit filed. kookie-flow.tsx:1181 `store.getState().setHoveredSocketId(hoveredSocket);` with no comparison; utils/geometry.ts:335-339 mints a fresh literal `return { entityId: socket.entityId, socketId: socket.socketId, isInput: socket.isInput };` per call; core/store.ts:611 `setHoveredSocketId: (hoveredSocketId) => set({ hoveredSocketId }),` sets unconditionally; sockets.tsx:327-332 sets the coarse dirtyRef. So every move WHILE OVER A SOCKET is a second full rebuild. The idle branch at kookie-flow.tsx:1545-1550 already guards field-by-field (and omits `isInput`).

What the coarse flag costs, at sockets.tsx:598-676: `socketRanges.clear()` then a loop over ALL `entities` calling `writeEntitySockets`, which per socket writes a 16-float matrix plus colors/hovered/connected/validTarget/invalidHover, then `markSocketBuffersForUpload` (sockets.tsx:93-100) sets needsUpdate on all six attributes plus `bgMesh.instanceMatrix.needsUpdate = true`. No updateRange anywhere, so three.js re-uploads the full capacity-sized arrays: seven buffer uploads per pointermove, sized by the whole graph. There is no culling in this file (the comment at :322 records viewport subscription was removed deliberately), so it is O(all sockets), not O(visible).

## What a person experiences

Nothing changes on screen — the fix is byte-identical output by construction, because validTarget and invalidHover depend on the draft's SOURCE and the hovered socket, never on the pointer position. What a person feels is frame cost during a connection drag, and it scales with the size of the graph rather than with what is on screen. Every pointermove walks every entity's inputs and outputs, rewrites six attributes and a 16-float matrix per socket, and re-uploads seven full capacity-sized buffers. At the plan's own 2000-entity baseline that is the whole socket set rewritten ~60 times per gesture. (The byte figure is derived from the buffer shapes at sockets.tsx:42-55, not measured — I am read-only.) Dragging a connection is the one gesture where the user is looking for a precise target, and it is the gesture this makes worst.

## Proposed fix

Two edits, one per leak. Neither needs the "attribute-only path" the plan sketches — that is a larger change and is not required to close the defect.

1. THE DRAFT (closes the unconditional half). sockets.tsx:334, narrow the selector to the only field the renderer reads:
     (state) => state.connectionDraft?.source ?? null
   `source` is copied by reference through the spread at store.ts:649, so its identity is stable for the life of a draft: two notifications per gesture instead of sixty. Safe because every draft is bracketed by a null — `startConnectionDraft` (kookie-flow.tsx:967) is handed a fresh literal from geometry.ts:335, and all three exits (kookie-flow.tsx:1119, :1653, :2012) go through `cancelConnectionDraft` (store.ts:656) which nulls both fields.

2. THE HOVER (closes the hovered half). Cheapest correct home is the store action, store.ts:611:
     setHoveredSocketId: (hoveredSocketId) => {
       const prev = get().hoveredSocketId;
       if (prev?.entityId === hoveredSocketId?.entityId &&
           prev?.socketId === hoveredSocketId?.socketId &&
           prev?.isInput === hoveredSocketId?.isInput) return;
       set({ hoveredSocketId });
     },
   One site instead of two, it cannot be forgotten by a future caller, and it fixes the idle branch's missing `isInput` term (kookie-flow.tsx:1546-1547 compares entityId and socketId only, while socket ids are scoped per direction — the connected-set keys at sockets.tsx:445/:482 are `${entity}:${socket}:input|output`). The call-site alternative is to add `hoveredSocketId` to the destructure at kookie-flow.tsx:1170 and wrap :1181 in the same three-field test.

Adjacent, same shape, not required for C15: entity-selection.tsx:320 `store.subscribe((state) => state.connectionDraft, markHandleDirty)` also fires every pointermove; it needs presence only, so `(state) => state.connectionDraft !== null`.

## What could regress

Three ways, and the dangerous one is that NO existing law catches it.

1. Over-fix. Deleting the hover subscription (sockets.tsx:327-332), or getting the comparison wrong, kills hover feedback: the socket stops scaling (vertex `pos * (1.0 + aHovered * 0.3)`) and stops brightening (fragment `mix(color, color * 1.4, vHovered * notInvalid)`), and invalid-target red stops arriving. NOTHING in the tree sees this. behaviors.mjs has no hover law at all — the socket section asserts only "pressing a painted socket starts a connection" (:561) — and no unit test mounts this component. A fix that deletes the feature passes every law today AND passes any naive "the cost went down" law, which is exactly why the proof below needs its vacuity arm.

2. Narrowing the draft selector. If `source` were ever mutated in place, or two consecutive drafts carried the same `source` object with no null between, valid-target highlighting would not repaint on the second draft. Impossible today (see the bracketing argument above) but it is a new invariant, so it needs pinning rather than assuming.

3. Staleness of validTarget/invalidHover if the graph changes mid-draft. Already covered and must stay covered: `unsubEntities` (sockets.tsx:311) and `unsubEdges` (sockets.tsx:339) still set the coarse flag, so an entity or edge change during a draft still forces a full rebuild.

## The law that proves it

THE EXISTING INSTRUMENT CANNOT SEE THIS FIX, and that must be dealt with before the commit rather than after. counts.mjs reports `instancesPerFrame` from `gl.instancesDrawn`, which fixture/app.tsx:160-168 sums from the instanceCount argument of drawElementsInstanced. Both socket meshes keep drawing `clampedCount` instances every frame under frameloop="always" whether or not a single buffer was rewritten. Draw calls, instances drawn and React commits are all unchanged by C15. Shipping against today's spike reproduces fix 11 and fix 17 — "correct by inspection, recorded as unmeasured".

INSTRUMENT (fixture/app.tsx, beside the existing wraps at :158-170, reset at :325-331): wrap `bufferSubData` and `bufferData` on WebGL2RenderingContext.prototype, counting calls and summing `srcData.byteLength` into `gl.bufferUploads` / `gl.bufferBytes`; counts.mjs divides by frames like every other figure. This reads the bytes actually crossing to the driver, not a counter the component keeps about itself — three.js flushes a dirty InstancedBufferAttribute through WebGLAttributes → gl.bufferSubData, so `markSocketBuffersForUpload` plus `instanceMatrix.needsUpdate` is precisely seven uploads this counts.

LAW, four arms. The gesture matters as much as the assertion, because the two leaks fire under different pointer paths.
  A1 `connection-drag-empty` — press an output socket, drag 60 moves across BLANK canvas.
  A2 `connection-drag-crossing` — press an output socket, drag along a path that PASSES OVER other entities' sockets.
  Run both at --count=200 and --count=2000 and assert bufferBytesPerFrame does not scale with graph size: bytes@2000 < 2 x bytes@200. (Pre-fix it tracks the graph: the socket rebuild is O(all sockets) with no culling, and the uploads are capacity-sized.)
  A3 VACUITY: bufferBytesPerFrame during each window must be > 0 — the connection line updates every frame, so a zero means the counter is dead, which is the answer this codebase most wants to hear.
  A4 FEATURE-ALIVE: press a socket, move onto exactly ONE other socket, require (i) bufferBytes to rise across that transition and (ii) `__harness.readPixel` at that socket's centre to change under ?preserveBuffer=1 — the shader scales it 1.3x and multiplies its colour by 1.4, both readable.

SABOTAGE — three, and each must kill a DIFFERENT arm:
  S1 revert sockets.tsx:334 to `(state) => state.connectionDraft`. A1 AND A2 go red; bytes/frame returns to tracking count.
  S2 revert kookie-flow.tsx:1181 to the unconditional `setHoveredSocketId(hoveredSocket)` (equivalently, drop the `isInput` term from the store guard and hover an input whose id matches an output on the same entity). A1 STAYS GREEN and only A2 goes red. This is the discriminating input the project's rule demands: a connection drag over empty canvas cannot tell the hover fix from no fix, so a single-window law here is a law about the special case wearing the general one's name. If S2 leaves A2 green, the drag path is not crossing a socket and the law is measuring nothing.
  S3 delete the `unsubHoveredSocket` subscription at sockets.tsx:327-332 entirely. A1, A2 and A3 all STAY GREEN — cost went down, which is what the naive law rewards — and only A4 goes red. This is the over-fix guard.
Pin the new invariant too: two consecutive drags from the SAME socket must each light valid targets (falsified by hoisting the SocketHandle at geometry.ts:335 to module scope and mutating it in place).

## What the critics said

### exists

Only a precision nit, not a defect in the finding. The headline "rebuild on every pointermove" is literally once per FRAME in which at least one pointermove landed, since the rebuild runs inside useFrame and the dirty flag coalesces multiple events per frame — the finding's own "~60 times per gesture" figure already reflects this, so the severity is unchanged, but a law measuring the fix should count frames/rebuilds rather than expecting a 1:1 ratio with pointermove events. Also worth stating explicitly in the plan: half (b) does not fire while dragging over empty canvas (null -> null is Object.is-equal, no notification), so it is correctly scoped to moves over a socket and to the enter/leave transitions — a benchmark whose drag window crosses no socket will measure only half (a), which is exactly the gap the finding already notes at counts.mjs:205-217.

### safety

The finding's core claim survives, but one stated benefit of the recommended home is FALSE and must not go into the commit message.

"[the store guard] fixes the idle branch's missing `isInput` term (kookie-flow.tsx:1546-1547...)" — it cannot. The idle branch guard at :1545-1550 short-circuits BEFORE calling the store:

    if (newHoveredSocket?.entityId !== hoveredSocketId?.entityId ||
        newHoveredSocket?.socketId !== hoveredSocketId?.socketId) {
      store.getState().setHoveredSocketId(newHoveredSocket);
    }

When the two handles agree on entityId and socketId but differ on isInput, `setHoveredSocketId` is never called, so a guard living inside it never runs. That bug (reachable when one entity has an input and an output sharing a socket id — nothing forbids it, and the connected-set keys at sockets.tsx:445/482 are direction-scoped precisely because ids are per-direction) survives the fix untouched. If it is meant to be closed, the call-site test at :1546-1547 must gain the isInput term, or that whole `if` must be deleted in favour of the store guard. Deleting it is the better shape — it leaves one home, which is the fix's own stated argument — but it is a THIRD edit, not a consequence of the second.

Two smaller amendments:

1. Public-surface note. `FlowState`/`FlowStore` are exported (src/index.ts:83) and the store instance is reachable by consumers (the harness drives it as `window.__harness.store`). So `setHoveredSocketId` is a public action and deduping changes its notification semantics for any external subscriber. The change is benign — the suppressed notification carries a deep-equal value — but it is an API-visible change and should be stated rather than discovered.

2. The finding's "byte-identical output by construction" is right, and the reason is stronger than the one given. It says validTarget/invalidHover "depend on the draft's SOURCE and the hovered socket, never on the pointer position". The load-bearing half is that sockets.tsx never reads `draft.isValid` AT ALL — and `isValid` is the field that carries the cycle check computed at kookie-flow.tsx:1196-1203. So the socket's own red and the connection LINE's red are already two different predicates today (a cycle-creating but type-compatible target reddens the line and leaves the socket green), and the fix does not touch that divergence. Anyone reviewing this will reach for "but isValid changes every move, so narrowing to source must lose the red socket"; the answer is that the sockets renderer computes its own validity and the line is repainted by an unconditional useFrame under frameloop="always" (kookie-flow.tsx:2322), independent of any subscription.

### minimal

Four corrections, none fatal. (1) UNIT SLIP: "seven buffer uploads per pointermove" is wrong. The rebuild is dirtyRef set by the subscriber and consumed in useFrame (sockets.tsx:509), so several pointermoves inside one frame coalesce into ONE rebuild. It is per FRAME while dragging; the user-visible paragraph's "~60 times per gesture" is the correct figure. (2) THE STORE-HOME JUSTIFICATION IS FALSE AS WRITTEN: a guard inside setHoveredSocketId cannot fix the idle branch's missing isInput term, because that branch's own `if` at kookie-flow.tsx:1545-1548 suppresses the CALL — with old {e1,'a',input} and new {e1,'a',output} both compared terms are equal, no call is made, and the store guard is never consulted. To collect that benefit the call-site `if` must also be deleted so the store really is the single home; the proposal does not say this. (3) A PARTIAL EXISTING IDIOM IS NOT CITED: `{ equalityFn: shallow }` from zustand/shallow is already used at widgets-layer.tsx:416,427 and would close the HOVER half locally with one option object and no change to a public store action's semantics. It does NOT close the draft half — shallow compares one level and mouseWorld is a fresh nested object every move — so the narrowed selector remains the only correct spelling there. This is an alternative home for edit 2, not a reason to drop either edit. (4) IMPACT IS UNDERSTATED, NOT OVERSTATED, on the JS side: the finding leads with buffer uploads, but writeEntitySockets also performs, per socket per frame, a THREE.Color string parse (tempColor.set), two template-string allocations for the connected-set keys, and an areTypesCompatible call while a draft is live — allocations in a hot path, which this repo's own CLAUDE.md marks UNACCEPTABLE. At the harness default of 1000 entities that is thousands of string allocations and colour parses per frame.
