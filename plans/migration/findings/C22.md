# C22 — risk medium, proof behaviour-browser, depends on nothing

## Is it still there

Not in the fixed list: `plans/migration/audit-findings.md` records fixes 1–17 and none touch `widgets-layer.tsx` or `StyleContext.tsx`. Every line the audit cites is still at the cited line number, unchanged.

**#31 — the snapshot gate.** `widgets-layer.tsx:224-225` takes a one-shot snapshot:
```ts
const [entities, setEntities] = useState(() => store.getState().entities);
const [connectedSockets, setConnectedSockets] = useState(() => store.getState().connectedSockets);
```
and the only thing that ever refreshes it is `widgets-layer.tsx:420-428`, which gates twice — once in the selector, once in the setter:
```ts
const unsubscribeState = store.subscribe(
  (state) => ({ entitiesLen: state.entities.length, socketsSize: state.connectedSockets.size }),
  ({ entitiesLen, socketsSize }) => {
    const state = store.getState();
    setEntities((prev) => (prev.length !== entitiesLen ? state.entities : prev));
    setConnectedSockets((prev) => (prev.size !== socketsSize ? state.connectedSockets : prev));
  },
  { equalityFn: shallow }
);
```
Because the SELECTOR is shallow-compared on `{entitiesLen, socketsSize}`, the listener does not even run for a same-length replacement. `widgetConfigs` (`:233-274`) reads that stale array, and the render at `:462-497` pulls `entity.color`, `entity.data.values[socket.id]` and `socket` out of it.

The reachable path is the ordinary controlled-component contract. `FlowSync` (`kookie-flow.tsx:2380-2382`) is `useEffect(() => { store.getState().setEntities(entities); }, [entities, store])`, and `store.ts:578-586` `setEntities` replaces the array wholesale. So a consumer handing `KookieFlow` a new `entities` array of the SAME length — one entity with a new `color`, an extra input socket, or a new `data.values` — publishes it to the store, every GL layer follows, and the widget layer does not.

There is a fifth case the audit's "same length gate" wording covers but does not enumerate, and it is the cleanest law input in the set: `connectedSockets` is rebuilt as a fresh Set keyed `` `${edge.target}:${edge.targetSocket}` `` (`store.ts:465-473`). A rewire — the consumer's `edges` prop moving one edge from `n1:in-0` to `n1:in-1` — goes through `FlowSync`'s `store.getState().setEdges(edges)` (`kookie-flow.tsx:2419`) in ONE `set`, so `size` stays 1 while the members change. The widget on the freed socket never reappears and the widget on the newly connected socket never disappears.

Note what is NOT stale: `updatePositions` (`:277-383`) reads `store.getState().entityMap` live at `:283/:313`, so position and size track correctly. The widget is *positioned* against the live entity and *rendered* from a mount-time snapshot. That is why the defect is invisible during a drag and only shows on a content change.

**#64 — `widgets-layer.tsx:119`.** `const [value, setValue] = useState(initialValue ?? config.defaultValue);` — React ignores the initializer after mount. The memo comparator at `:161` does compare `prev.initialValue === next.initialValue`, so `SocketWidget` would re-render once the snapshot refreshes, but `value` would not move. Case (a) is blocked twice over.

**#86 — `widgets-layer.tsx:228-229/245/274`.** The ref is written in the render body and read by a memo that omits it:
```ts
const widgetTypesRef = useRef(widgetTypes);
widgetTypesRef.current = widgetTypes;            // :228-229, render body
...
const currentWidgetTypes = widgetTypesRef.current; // :245, inside the memo
}, [entities, connectedSockets, socketTypes]);     // :274 — no widgetTypes
```
**But I could not confirm this one is user-visible today, and the reason matters.** `kookie-flow.tsx:144` allocates in the render body with no memo — `const resolvedSocketTypes = { ...DEFAULT_SOCKET_TYPES, ...socketTypes };` — and `socketTypes = {}` at `:98` is itself a fresh default per render. `ThemedFlowContainer`'s `useMemo(() => resolveSocketTypes(socketTypes, tokens), [socketTypes, tokens])` (`:299-302`) therefore recomputes every render, so `WidgetsLayer.socketTypes` has a new identity on every `KookieFlow` render, which forces the `widgetConfigs` memo to recompute anyway — reading the ref that was just written. Since a `widgetTypes` swap necessarily re-renders `KookieFlow` (it is a prop of it), and `WidgetsLayer` is not in the public surface (`src/index.ts` has no `export *` and no `from './components'`), I believe #86 is currently masked. It is a live trap, not a live defect: the mask is an obvious perf fix of exactly the kind C19's batch is full of, and the day someone stabilises `resolvedSocketTypes`, `widgetTypes` swaps silently stop resolving with no law watching.

**#65 — `StyleContext.tsx:122`.** `}, [size, variant, radius, header, accentHeader, entityStyle, tokens]);` — an object identity in the deps. `entityStyle` is public API (`types/index.ts:863`), so an inline literal mints a new `resolved` and `socketLayout` on every consumer render. Downstream, `nodes.tsx:115` is `useMemo(() => new THREE.ShaderMaterial({...}), [resolvedStyle])` (deps at `:315`) and there is no `dispose` anywhere in the file — a compiled GLSL program per parent render. It also lands inside my own second file: `useSocketLayout()` at `widgets-layer.tsx:211` feeds `updatePositions`'s deps (`:383`), which feeds the layout effect's deps (`:438`), so the ResizeObserver and both store subscriptions are torn down and re-registered on every such render.

The repo has already conceded the shape one hop downstream: `socket-layout-cache.ts:85-91` compares the layout BY VALUE with the comment "`StyleProvider`'s memo lists `entityStyle`, so a caller passing an inline object literal produces a fresh `socketLayout` on every render" — the workaround exists, the cause does not.

## What a person experiences

Four things a consumer of `KookieFlow` does, that produce nothing:

1. Give an entity a `color` — the GL node repaints with the accent, the widgets sitting on it keep the default theme forever. (`ThemeComponent` wrap, `widgets-layer.tsx:143-151`.)
2. Add an input socket to an existing entity — the socket is drawn, its row exists, and no widget appears in it.
3. Rewire an edge onto a different input of the same entity — the freed socket's widget stays hidden and the newly connected socket's widget stays visible, i.e. two widgets are wrong at once, and the visible one is now sitting on a connected socket.
4. Write a value into `entity.data.values` from outside — the widget keeps whatever it had at mount. A widget cannot be driven from outside at all; it is write-only.

All four are invisible during pan, zoom and drag, because positions come from `store.getState()` live. They only show when content changes, which is why nothing caught them: `harness/behaviors.mjs` never mounts widgets (`showWidgets={p.widgets}`, default off), `counts.mjs:63` never passes `widgets=1`, and no file under `src/**/*.test.*` imports `widgets-layer.tsx` or `StyleContext.tsx`.

#65 is not directly visible; it is a shader program leaked per parent render for anyone who passes an inline `entityStyle`, plus a ResizeObserver and two store subscriptions re-registered at the same rate.

## Proposed fix

**1. `widgets-layer.tsx:420-428` — subscribe to the store's own structure signals, not to lengths.** Both gates go; the selector stays O(1):
```ts
const unsubscribeState = store.subscribe(
  (state) => ({ topology: state.topologyVersion, connected: state.connectedSockets }),
  () => {
    const s = store.getState();
    setEntities(s.entities);
    setConnectedSockets(s.connectedSockets);
  },
  { equalityFn: shallow }
);
```
`topologyVersion` is bumped unconditionally by `setEntities` (`store.ts:585`) and is already the established "structure changed, re-snapshot" signal here — `image-entities.tsx:277` and `reroute-nodes.tsx:179` both subscribe to exactly it, so this is a promotion of an in-repo pattern, not an invention. `connectedSockets` is a fresh Set on every edge change (`store.ts:465-473`) and is never rebuilt on a node drag, which is what makes case 3 reachable without touching the frame path.

**Stated gap rather than smuggled fix:** `applyEntityChanges` bumps `topologyVersion` only `...(topologyChanged ? ... : {})` (`store.ts:780`), so a `data`-only change made by calling that store action directly is still invisible. In `KookieFlow` every such change round-trips through the consumer's `entities` prop → `FlowSync` → `setEntities`, which does bump, so the gap is only reachable by someone driving the store through the exported `useFlowStoreApi`. Closing it means bumping on `data` in `store.ts`, which is outside C22's two files and also re-renders `image-entities` and `reroute-nodes` — flag it, do not fold it in.

**2. `widgets-layer.tsx:228-229, 245, 274` — delete the ref, name the prop.** Remove `widgetTypesRef` entirely, use `widgetTypes` directly at `:245`, and make `:274` read `}, [entities, connectedSockets, socketTypes, widgetTypes]);`. Costs nothing today (`socketTypes` already churns per render); stops costing nothing the day that is fixed.

**3. `widgets-layer.tsx:119` — local state + sync + dirty flag.** `useEffect(() => { if (!dirtyRef.current) setValue(initialValue ?? config.defaultValue); }, [initialValue, config.defaultValue])`, with `dirtyRef.current = true` set in `handleChange` (`:121-127`) and cleared when the incoming `initialValue` matches what was last sent. **This is the one call I would not make alone** — see couldRegress. Fully controlled is wrong here (the shipped demo never writes back, so every widget freezes while typing); no dirty flag is also wrong (a consumer that echoes `onWidgetChange` into `entities` resets the field on every keystroke). It is a product decision and belongs to Kushagra.

**4. `StyleContext.tsx:105-122` — stabilise the object, do not widen the deps.** Use React's documented render-phase adjustment rather than a render-body ref write (a render-body ref write is literally what #86 is about, three files over):
```ts
const [stableStyle, setStableStyle] = useState(entityStyle);
if (!sameOverrides(stableStyle, entityStyle)) setStableStyle(entityStyle);
```
where `sameOverrides` compares the five flat fields of `EntityStyleOverrides` (`types/index.ts:720-731`: `background`, `borderColor`, `borderWidth`, `borderRadius`, `shadow`) — all primitives, so an O(1) allocation-free compare, the same spelling as `sameLayout` at `socket-layout-cache.ts:91`. Then `stableStyle` replaces `entityStyle` at `:110`, `:119` and in the dep list at `:122`. Document the prop as wanting a stable reference, as the audit says.

## What could regress

**The naive fix is worse than the bug, and I verified the mechanism rather than trusting the audit.** `updateEntityPositions` does `const nextEntities = [...entities]` (`store.ts:1012`) and `set({ entities: nextEntities, positionVersion: positionVersion + 1 })` (`store.ts:1050`) on every pointermove. So subscribing to `state.entities` by reference — the filed fix — re-renders `WidgetsLayer` once per drag frame. That is not one re-render: `widgetConfigs` (`:233`) rebuilds a Map over every entity × input, `widgetEntries` (`:455`) rebuilds an array, and every wrapper's `ref` at `:470-476` is a fresh inline closure, so React detaches (calls with `null`, deleting the key from `widgetRefsMap`) and re-attaches every widget's DOM ref per frame. Against 1000 entities that is a per-frame O(n) rebuild in the layer whose entire design premise (`:5-14`) is "no React re-renders on pan/zoom".

**A `topologyVersion` subscription is once-per-gesture, not never.** `onEntitiesChange` for a drag fires at pointer-up (`kookie-flow.tsx:1707-1717`), not per move, so `FlowSync` → `setEntities` → `topologyVersion++` lands once per completed drag. Correct, but new: the widget snapshot now re-renders at mouseup where it previously never did. `counts.mjs`'s `drag-node` window should be read for a commit spike at gesture end.

**#64 is the contested one.** With no dirty flag, a consumer echoing `onWidgetChange` back into `entities` makes the field un-typeable — every keystroke resets it. With a dirty flag, an external write during typing is silently dropped. Both are defensible; picking one silently is not.

**#65's stabilisation moves `socketLayout` identity**, which is a dep of `updatePositions` (`:383`) and of the layout effect (`:438`). It removes teardown/rebuild of the ResizeObserver and both subscriptions — a win, but any law counting subscription churn changes its answer. It also reduces how often `nodes.tsx:115` mints a material; it does not stop the mint, and disposal is C25's.

**Adding `widgetTypes` to `:274`** means a consumer passing an inline `widgetTypes={{...}}` recomputes the config map every render. That is already true today via `socketTypes`, so no new cost — it becomes one the day `kookie-flow.tsx:144` is stabilised, which is why the prop wants the same "keep this stable" note `entityStyle` gets.

**Existing laws that would catch a bad fix:** none. That is the finding behind the finding here — `harness/behaviors.mjs` never sets `widgets=1`, `counts.mjs:63` never sets it, and nothing in `src/**/*.test.*` imports either file. Every guard below has to be written.

## The law that proves it

**Tier: the jsdom `dom` project** (`vitest.config.ts` — the file MUST be named `*.dom.test.tsx`; a plain `.test.tsx` lands in the `node` project and dies on `document`). `WidgetsLayer` needs only two React contexts, no WebGL, so it mounts directly:

```tsx
// src/components/widgets-layer.dom.test.tsx
const SOCKET_TYPES = { float: { widget: 'text' } } as Record<string, SocketType>; // module scope — load-bearing, see below
let renders = 0;
function Stub({ value }: WidgetProps) { renders++; return <output data-widget>{String(value ?? '')}</output>; }
const ThemeStub = ({ accentColor, children }) => <div data-accent={accentColor}>{children}</div>;
let api: FlowStore; function Grab() { api = useFlowStoreApi(); return null; }

render(
  <FlowProvider initialState={{ entities: START, edges: EDGES }}>
    <StyleProvider><Grab />
      <WidgetsLayer socketTypes={SOCKET_TYPES} widgetTypes={{ text: Stub }} ThemeComponent={ThemeStub} />
    </StyleProvider>
  </FlowProvider>
);
```
Every assertion reads committed DOM after a real store action — not a token name, not a hook return, not the memo's inputs.

**L1 accent.** `START = [{ id:'n1', position:{x:0,y:0}, inputs:[{id:'in-0',type:'float'}] }]`, no `color`. Then `act(() => api.getState().setEntities([{ ...START[0], color: 'crimson' }]))`; assert `container.querySelector('[data-accent]')!.getAttribute('data-accent') === 'crimson'`.
**L2 new socket.** `act(() => api.getState().setEntities([{ ...START[0], inputs:[{id:'in-0',type:'float'},{id:'in-1',type:'float'}] }]))`; assert `container.querySelectorAll('[data-widget]').length === 2`.
**L3 rewire.** `START` has two inputs and `EDGES = [{ id:'e', source:'n0', target:'n1', targetSocket:'in-0' }]`. `act(() => api.getState().setEdges([{ ...EDGES[0], targetSocket:'in-1' }]))`; assert the rendered `data-socket-index` set flips `{1}` → `{0}`.
**L4 widgetTypes swap.** `rerender` the same tree with `widgetTypes={{ text: StubB }}` and the SAME `SOCKET_TYPES` reference; assert StubB's marker is in the DOM.
**L5 value sync (#64).** `act(() => api.getState().setEntities([{ ...START[0], data:{ values:{ 'in-0':'B' } } }]))`; assert `querySelector('[data-widget]')!.textContent === 'B'`.
**L6 the regression guard.** `const before = renders; act(() => { for (let i=0;i<30;i++) api.getState().updateEntityPositions([{ id:'n1', position:{x:i,y:0} }]); }); expect(renders).toBe(before);` — **zero, not "small"**.
**L7 #65** — `src/contexts/style-context.dom.test.tsx`: a `Reader` pushing `useResolvedStyle()` into an array, rendered three times as `<StyleProvider entityStyle={{ borderWidth: 1 }}>` written as an **inline literal at each render**; assert `new Set(seen).size === 1`.

**The vacuity property, which is the whole design.** Every fixture is one where the general case and the special case give DIFFERENT answers, because the special case is what the buggy code already handles:
- L1/L2/L5 keep the entity count at **1 before and after**. A fixture that added an entity passes against the shipped code — the length gate opens — and would be a law about entity insertion wearing the snapshot's name.
- L3 keeps `connectedSockets.size` at **1 before and after**. A fixture that added an edge passes against the shipped code.
- L4's `socketTypes` must be **one hoisted module const**. Written inline it passes against the shipped code, because `kookie-flow.tsx:144` is precisely the accidental instability that masks #86 in production — an inline-`socketTypes` law would be a law about the mask.
- L7's `entityStyle` must be an **inline literal that is shallow-equal every time and reference-different every time**. Hoisted to a const it passes against the shipped code.

**The exact sabotages that must make each law fail:**
- Restore `setEntities((prev) => (prev.length !== entitiesLen ? state.entities : prev))` at `:424` → **L1, L2, L5 fail.**
- Restore the selector `(state) => ({ entitiesLen: state.entities.length, socketsSize: state.connectedSockets.size })` at `:421` → **L1, L2, L3 fail** (the listener never runs at all).
- Restore only `setConnectedSockets((prev) => (prev.size !== socketsSize ? ... : prev))` at `:425` → **L3 alone fails.**
- Drop `widgetTypes` from `:274` and put `widgetTypesRef` back → **L4 fails.**
- Restore the bare `useState(initialValue ?? config.defaultValue)` at `:119` → **L5 fails.**
- Change the C22 subscription selector to `(state) => state.entities` (the filed fix) → **L6 fails, reporting 30 extra renders per widget** and every other law stays green, which is the point: this is the sabotage that separates "the snapshot refreshes" from "the snapshot refreshes without re-entering the frame path".
- Put `entityStyle` back in the dep list at `StyleContext.tsx:122` → **L7 fails at `expected 3 to be 1`.**

**Calibration, because a green suite over an unmounted subject is this repo's recorded failure mode twice over:** before trusting any of them, delete `WidgetsLayer` from the mount and confirm L1–L6 fail with "not found" rather than passing over an empty container — and confirm the file is actually collected by the `dom` project, not silently skipped.

**Harness half (regression, not correctness):** `counts.mjs:63` must gain `&widgets=1` — today it never mounts a widget, so the drag-frame commit count for this layer has never been measured at all. Read `reactCommits` for the `drag-node` window before and after; it must not move, and the mouseup commit noted above must be a single commit, not one per widget per frame. The #65 leak is confirmable only with GL (`renderer.info.programs` flat across N parent renders with an inline `entityStyle`) — that instrument belongs with C24/C25 and I would not build it here.

## What the critics said

### exists

Two refinements, neither of which rescues the finding. (a) The #86 mask is stronger than reported and it changes the fix's cost estimate: kookie-flow.tsx:144 allocates resolvedSocketTypes unmemoised, so ThemedFlowContainer's memo (:303-306) mints a new identity every render, which ALSO re-runs FlowSync's second effect (deps [edges, socketTypes, store]) -> setEdges -> topologyVersion+1 and a fresh connectedSockets Set on EVERY KookieFlow render. So proposed fix #1's "once per gesture" framing understates the churn: subscribing to topologyVersion re-renders WidgetsLayer on every parent render until :144 is memoised — the two changes should ship together, and the "stated gap" about applyEntityChanges not bumping on data-only changes is correspondingly less material. (b) One user-visible symptom is missing from the four listed, and it is worse than an absent widget: data-socket-index (:478) is written at mount from the snapshot's inputIndex and read back by updatePositions (:337) to index the LIVE entityLayout.inputs (:341), so inserting a socket at the front of an existing entity leaves every already-mounted widget positioned on the WRONG row of a live layout. Socket removal is half-covered by accident (the lookup returns undefined and the widget hides), which is another reason a length-based law would look green.

### minimal

Four things the fix gets wrong as a minimal, necessary change.

**1. The proposal's own regression list misses the one that bites, and it is caused by dropping BOTH setter guards.** `resolvedSocketTypes` is a fresh object literal in KookieFlow's render body (`kookie-flow.tsx:145`), so `ThemedFlowContainer`'s `useMemo` (`:299-302`) recomputes every render, so `FlowSync`'s edge effect — deps `[edges, socketTypes, store]` at `:2421` — re-runs on EVERY parent render and calls `setEdges(edges)`. That mints a fresh `connectedSockets` Set (`store.ts:591`) and bumps `topologyVersion` (`:593`). So an un-guarded topology listener fires on every consumer render, and because the Set is a new reference each time `setConnectedSockets` never bails out: WidgetsLayer takes an EXTRA render pass with a full `widgetConfigs` rebuild (O(entities × inputs), `:233-274`), a fresh `widgetEntries` array (`:455`), and a detach/reattach of every widget's inline `ref` closure (`:470-476`) — on top of the render it already does. "could regress" names only the per-frame reference subscription (correctly rejected) and the once-per-gesture cost; it does not name this. The in-repo precedent does NOT drop the guard: `image-entities.tsx:280-287` and `reroute-nodes.tsx:182-190` both subscribe broadly and then guard the setState with an element-wise VALUE compare. Keep a guard — just a correct one (compare the value, not `length`/`size`).

**2. The selector is one indirection wider than it needs to be.** Both precedents use the scalar `s => s.topologyVersion`; the proposal's `{topology, connected}` + `shallow` allocates an object on every store `set`, i.e. on every pointermove during a drag, in a file whose header claims allocation discipline. And `connectedSockets` is redundant: all eight writes to it bump `topologyVersion` in the same `set` (591/593, 829/832, 1262/1264, 1325/1327, 1641/1640, 1672/1671, 1777/1776, 1820/1819) plus `setEntities` at 585.

**3. The fix is bigger than C22.** Part 4 (#65, `StyleContext.tsx:122`) does not cause the staleness at all — re-registering the layout effect preserves the `useState` snapshot, so it is a separate perf/lifecycle finding (shader material churn with no `dispose`, subscription re-registration) that merely shares a file with C22. Bundling it turns a selector change into a four-file commit that touches public API prose (`entityStyle` "keep this stable"), `nodes.tsx` material lifetime and the already-shipped `socket-layout-cache` workaround. Part 3 (#64) is admitted to be a product decision and is the ONLY part that fixes case 4. Split both out; part 2 (#86) is admitted masked and is cheap enough to fold in, but it is not the defect.

**4. Case 3 is overstated as written.** The library's own hook never produces it: `use-graph.ts:156-168` `onConnect` only appends and the `remove` arms only splice, so every interactive connect/disconnect changes `connectedSockets.size` and the existing gate DOES fire. Case 3 needs a consumer writing their own edges reducer that swaps a `targetSocket` in one array update — reachable through the documented controlled contract and still the cleanest law input, but not what a person hits by dragging in the shipped demo. Cases 1, 2 and 4 are reachable exactly as described. Also a precision point the headline hides: the two gates are independent, so on a connect the `connectedSockets` half refreshes while the `entities` half stays stale — "the snapshot never refreshes" is really "the two halves refresh on different, wrong, quantities", and any law has to read both.
