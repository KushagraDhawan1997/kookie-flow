## What a person experiences

Four separate things. (1) A user in an iOS in-app WebView (Facebook, Instagram, Slack, any `SFSafariViewController`-adjacent shell) gets a multisampled backbuffer allocated and resolved every frame for no visual benefit — the branch that was written to spare them does the opposite. (2) On iOS Safari, a two-finger pinch over the canvas zooms the PAGE as well as the graph: the visual viewport scales the whole document while the graph zooms underneath it. (3) The browser's own context menu opens over the canvas on every right-click, and on macOS on every Ctrl+click — which is also the additive-select chord, so multi-selecting on a Mac pops the OS menu on top of the selection. (4) The minimap goes blurry the moment devicePixelRatio changes: Ctrl+/Ctrl− browser zoom, or dragging the window from a Retina display to an external 1× monitor. Its backing store stays at the mount-time ratio while CSS stretches it.

## Proposed fix

Four independent edits.

**(a) #97 — delete the sniff.** Remove kookie-flow.tsx:83-85 entirely (`isSafari` has exactly one reader). At :2301 write `antialias: false,` and replace the comment at :2300 with the real reason — every silhouette is SDF-antialiased in the fragment shader (`fwidth`/`smoothstep`, nodes.tsx:280, entity-selection.tsx:143/268, edges.tsx:95, connection-line.tsx:46, grid.tsx:69-76), so MSAA on the default framebuffer resolves an already-antialiased image and costs a multisampled backbuffer per frame. Fix the three stale "Safari" comments at :2297, :2305, :2308 in the same commit (doc–code drift). `false` rather than `true` is the recommendation but it is the sign-off half of this item; either value is a correct fix for the *defect*, which is that the decision is made by a string.

**(b) #72 — move `touchmove` off React.** Convert `handleTouchMove` (kookie-flow.tsx:2140-2192) into a native listener registered in an effect beside the wheel effect at :766-804, body unchanged except the parameter type (`(e: TouchEvent)` — `changedTouches` is identical on both):
```ts
useEffect(() => {
  const container = containerRef.current;
  if (!container) return;
  const onTouchMove = (e: TouchEvent) => { /* body of :2141-2191, unchanged */ };
  container.addEventListener('touchmove', onTouchMove, { passive: false });
  return () => container.removeEventListener('touchmove', onTouchMove);
}, [store, minZoom, maxZoom, updateViewport]);
```
and delete `onTouchMove={handleTouchMove}` at :2241. `onTouchStart`/`onTouchEnd`/`onTouchCancel` stay on React — they never call `preventDefault`, and the shared `touchState` ref already crosses the boundary. Do NOT leave both bindings attached; the state map would take each move twice.

**(c) #113 — prevent unconditionally, except on editable targets.** kookie-flow.tsx:2103-2108 becomes:
```ts
// A contextmenu event carries button 2 (right-click) or 0 (macOS Ctrl+click, menu key) —
// never 1. Prevent it over the canvas; leave it for real form controls.
const handleContextMenu = useCallback((e: React.MouseEvent) => {
  const target = e.target as HTMLElement;
  if (target.tagName === 'INPUT' || target.tagName === 'TEXTAREA' || target.isContentEditable) return;
  e.preventDefault();
}, []);
```
The editable exemption is not optional: `WidgetsLayer` renders real `TextField`/`<input>` controls inside this same container (src/components/widgets/TextWidget.tsx:26, NumberWidget.tsx:56, TextareaWidget.tsx, ColorWidget.tsx:22), as does the consumer's `children` via `DOMLayer` (kookie-flow.tsx:354-358). The guard shape is copied verbatim from the existing keyboard guard at kookie-flow.tsx:1989-1991. This is the preventDefault half only — the Ctrl+click-as-additive-select question (:1742, :1882, :1897) is the separate sign-off the report files at line 543 and is NOT touched here.

**(d) #115 — watch DPR.** In minimap.tsx, hold the ratio in state and re-key the layout effect on it:
```ts
const [dpr, setDpr] = useState(() => (typeof window === 'undefined' ? 1 : window.devicePixelRatio || 1));
useEffect(() => {
  const mq = window.matchMedia(`(resolution: ${window.devicePixelRatio}dppx)`);
  const onChange = () => setDpr(window.devicePixelRatio || 1);
  mq.addEventListener('change', onChange);
  return () => mq.removeEventListener('change', onChange);
}, [dpr]);
```
Delete the local `const dpr = …` at :653 and add `dpr` to the deps at :676. Keying the effect on `dpr` is load-bearing: a `(resolution: Xdppx)` query only fires once, on leaving X, so each change must register a query for the new ratio. `setDpr` re-renders `Minimap`, which is legal here — it fires on a DPR change, not per frame, and the layout effect already resets the context transform by writing `canvas.width` before `ctx.scale`, so the scale cannot compound.

## What could regress

**(a) antialias.** Every non-WebKit user currently gets MSAA and would stop. Low visual risk by construction — the drawn geometry is screen-aligned instanced quads whose visible boundary is the shader's alpha, which MSAA does not sample — but it is a rasterisation change across the whole install base, which is why the plan marks it sign-off and demands a pixel proof. If the pixel tier shows movement, `antialias: true` unconditionally is the other correct answer to the same defect. Note the merge collision: this `glConfig`/`<Canvas>` block (kookie-flow.tsx:2297-2320) is the same block C24 edits for `camera.manual`.

**(b) touchmove.** Two failure modes, both from a half-done move. Leaving `onTouchMove={handleTouchMove}` bound while also registering natively makes every move update `touchState.current.touches` twice — harmless for a Map keyed by identifier, but the pinch would then run its zoom math twice per event and double the pan delta. And the native handler must not close over stale `minZoom`/`maxZoom`/`updateViewport`: the effect needs the wheel effect's exact dep list, or a pinch silently clamps to the mount-time zoom bounds — the C23 stale-closure class in a new listener.

**(c) contextmenu.** This removes the browser menu over the entire canvas: no "Save image as", no "Inspect", no spellcheck menu. The editable exemption keeps copy/paste alive in the socket widgets and in consumer overlay children, but a consumer who was deliberately relying on the native menu over the canvas loses it with no opt-out — there is no prop for this today. Do not "fix" it by attaching the preventDefault to `document` or `window`; that would suppress the menu across the whole host page.

**(d) DPR.** `setDpr` introduces a React render into `Minimap`, which the perf rules ban in hot paths — it is only reached on a DPR change, but a future refactor that widened that effect's triggers would put a render on the interaction path. Second: `matchMedia` and `MediaQueryList.addEventListener` must be feature-guarded for SSR/jsdom (the existing `typeof window === 'undefined'` guard in the initialiser covers mount; the effect body needs `matchMedia` to exist, which the jsdom tier stubs incompletely). Third: writing `canvas.width` clears the 2D context, so the `ctx.scale(dpr, dpr)` at :661 must stay AFTER the width/height writes, as it is now — reordering them would compound the transform on every DPR change.

Which existing law catches any of it: none. `grep -rn "isSafari|userAgent|contextmenu|devicePixelRatio" src/**/*.test.ts` returns nothing, and `grep -n "contextmenu|button: 'right'|touch|Touch|dispatchEvent" harness/behaviors.mjs` matches only the `chromium` import line. All four paths have zero coverage in the 196 unit laws and the 37 behaviours, which is why all four shipped.

## The law that proves it

Four laws. Every one reads the browser's computed output, and each names the input where the general and special cases disagree.

**L1 — `harness/behaviors.mjs`, "a two-finger touchmove is cancelled; a one-finger touchmove is not".** Install a BUBBLE-phase listener on `window` before the gesture (`window.addEventListener('touchmove', e => window.__tm.push(e.defaultPrevented), false)`) — bubble, not capture, because a capture listener on window runs before React's root-container listener and would read `false` on correct code. Drive real multi-touch through CDP `Input.dispatchTouchEvent` (Playwright's `page.touchscreen` only taps): `touchStart` with two touchPoints over the canvas, then `touchMove` with both points spread apart. Assert the recorded `defaultPrevented === true`. Second half, the discriminating input: a ONE-finger `touchStart` + `touchMove` must record `false`, because kookie-flow.tsx:2156 only prevents at `touches.length === 2`. **Sabotage that must make it fail:** change `{ passive: false }` back to `{ passive: true }` in the new effect — or equivalently re-bind the handler as `onTouchMove={handleTouchMove}` at :2241 and delete the native listener. Either flips the first assertion to `false` and prints Chrome's "Unable to preventDefault inside passive event listener invocation". The one-finger half is the vacuity guard: without it, a law that only asserts `true` passes against a blanket `e.preventDefault()` at the top of the handler, which would kill single-finger scrolling.

**L2 — `harness/behaviors.mjs`, "a right-click on the canvas is cancelled; one on a form control is not".** Same window bubble recorder for `contextmenu`. `page.mouse.click(x, y, { button: 'right' })` over empty canvas → `defaultPrevented === true`. Two controls, both required: right-click on a `WidgetsLayer` `<input>` (mount the fixture with `widgets=1`) → `false`; right-click on a DOM node OUTSIDE the flow container (the fixture's own page background) → `false`. **Sabotage:** restore `if (e.button === 1) {` around the `preventDefault` at :2105 — the first assertion fails with `expected false to be true`. Second sabotage, which is what the controls exist for: move the `preventDefault` to a `document`-level listener — the first assertion still passes and both controls fail. Without the controls this is a law about the special case wearing the general one's name.

**L3 — `harness/behaviors.mjs`, "the minimap canvas follows a DPR change".** Requires a fixture change: harness/fixture/app.tsx:499 currently passes `showMinimap={false}`, so gate it on a `?minimap=1` query. Launch the context at `deviceScaleFactor: 1`. Read `{ dpr: devicePixelRatio, backing: c.width, css: c.clientWidth }` off the minimap canvas and assert `dpr === 1 && backing === css` — this is the calibration half, and it is what tells a real pass from a context that was already at 2. Then `cdp.send('Emulation.setDeviceMetricsOverride', { width: 1280, height: 800, deviceScaleFactor: 2, mobile: false })`, wait two rAFs, re-read, and assert `dpr === 2 && backing === css * dpr`. Against the current code the second read is `dpr: 2, backing: 200, css: 200` → fails `expected 200 to be 400`. **Sabotage:** delete `dpr` from the layout effect's dep list at :676 (leaving the state and the matchMedia listener in place) — the state updates, the effect never re-runs, the assertion fails at exactly the same numbers. Second sabotage: register the media query without keying the effect on `dpr` — the first DPR change is caught and a second one is not, so extend the law to move the ratio 1 → 2 → 3 and assert after each.

**L4 — the UA removal, two halves, because neither is sufficient alone.**
*L4a, source law (new `src/components/platform-sniffing.test.ts`, node tier, the shape `src/utils/socket-geometry-home.test.ts` already establishes):* walk every `src/**/*.{ts,tsx}` and fail on `/navigator\s*\.\s*(userAgent|vendor|platform)|userAgentData/`, with a single named allow-list entry — `src/plugins/useKeyboardShortcuts.ts` — carrying the reason in the law (`mod` → Cmd/Ctrl is a keyboard convention with no feature test, and it reaches no GPU or rendering decision). The allow-list must be by FILE NAME, not a regex that would also excuse a re-added `isSafari`. **Sabotage:** paste kookie-flow.tsx:84-85 back — the law fails naming the file and line.
*L4b, browser law (extend `harness/spikes/`, or a behaviour):* for each of four UA strings, `browser.newContext({ userAgent })`, mount, and read the NEGOTIATED attribute — `window.__harness.canvas().getContext('webgl2').getContextAttributes().antialias` — never the object literal at :2298, which is the declared value. The four must include the pair the shipped regex splits: a macOS Safari UA (`… Version/17.4 Safari/605.1.15`, matches → `false` today) and a desktop Chrome UA (`… Chrome/122.0.0.0 Safari/537.36`, no match → `true` today), plus the two the finding is about — an iOS in-app WebView UA with no `Safari/` token, and a `CriOS/… Safari/604.1` UA. Assert all four agree. **This law needs its own calibration or it is worthless on SwiftShader:** in the same page create two throwaway canvases, `getContext('webgl2', {antialias:true})` and `getContext('webgl2', {antialias:false})`, read `getContextAttributes().antialias` off each, and ERROR (not pass) if they are equal — if the software rasteriser reports one value regardless, the environment cannot see this change and the law must say so rather than go green. **Sabotage:** restore `antialias: !isSafari` — the Safari and Chrome cells disagree and the law fails printing both UAs. Companion pixel proof for the sign-off half: the existing round-trip instrument (light→dark→light, no threshold) with a null control, run before and after the `antialias: false` flip.

## What the critics said

### exists

One nit that does not change the verdict: for the Chrome-on-iOS case the sniff's misclassification is benign in outcome — Chrome on iOS is WebKit-backed, so `antialias: false` happens to be the right value there even though the string test reached it for the wrong reason. The finding's user-visible section is already careful about this (it only claims harm for the in-app WebView case), so this is a nuance rather than an error.

### safety

Fix (a)'s central justification is FALSE, and its recommended value (`antialias: false`) is a real visual regression for every non-Safari user.

"Every silhouette is already antialiased in-shader, so MSAA is buying nothing for anyone" does not hold for edge ARROWHEADS. edges.tsx:985-1026 writes `uvs[uvIdx+1] = 0` and `perpendiculars = (0,0)` for all three arrow vertices, so the ribbon fragment shader computes `dist = abs(vUv.y) = 0` and `alpha = 1.0 - smoothstep(1.0 - uAASmooth, 1.0, 0.0) = 1.0` uniformly across the triangle. The arrowhead has ZERO in-shader antialiasing, and its two diagonal edges sit at arbitrary angles (perpendicular to the local edge direction, edges.tsx:973-976). MSAA on the default framebuffer is the only thing smoothing them. The report's cited proof set (nodes.tsx:280, entity-selection:143/268, edges.tsx:95, connection-line:46, grid:69-76) enumerates only the SDF quads, and edges.tsx:95 is precisely the ribbon-width smoothstep the arrow vertices opt out of. The "could regress" note — "the drawn geometry is screen-aligned instanced quads whose visible boundary is the shader's alpha" — is wrong for this one class of real geometry. (Four other shader files also carry no fwidth/smoothstep: selection-box, text-edit-cursor, image-entities, text-entities, text-renderer — axis-aligned quads, where MSAA matters far less.)

The safe value for (a) is `antialias: true` unconditionally. That still kills the defect (the decision stops being made by a UA string), still fixes the inverted iOS-WebView/CriOS cases, and changes rasterisation for nobody except real Safari — which is the population the dead branch was written to spare and, per the report's own reading of the regex, largely the only population it ever reached.

Second, the proof the plan asks for cannot see the regression: `grep markerEnd|markerStart harness/fixture/*.tsx` returns nothing, so no fixture edge renders an arrowhead. A pixel tier run against the current fixture would come back clean over a genuine visual change. If `antialias: false` is pursued anyway, the fixture must first grow an edge carrying `markerEnd` — otherwise the sign-off is a law about the special case wearing the general one's name.

Third, minor and disclosed: the (d) snippet calls `window.matchMedia` unguarded. src/test/setup.ts stubs ResizeObserver, pointer capture and PointerEvent specifically so components mount in jsdom, and does NOT stub matchMedia. No law breaks today (no .dom.test mounts Minimap), but the edit makes Minimap un-mountable in the jsdom tier. Guard it, or add the stub in the same commit.

### minimal

Four corrections; the first is a real existing mechanism the item does not account for.

1. **(c) is NOT a bug-fix, it is an API decision, and the codebase already has the mechanism.** `src/plugins/useContextMenu.ts` is a public export (`src/plugins/index.ts:14,20`) whose entire job is context-menu suppression + state, and whose documented pattern (its own JSDoc, lines 64-88) has the CONSUMER wrap `<KookieFlow>` in a div with `onContextMenu`, where the hook's handler calls `event.preventDefault()` and `event.stopPropagation()` (lines 113-125). Because contextmenu bubbles out of the canvas container to that wrapper, a consumer using the sanctioned plugin ALREADY gets the native menu suppressed today. That reframes the current non-suppression as the library's deliberate default (library does not suppress; consumer opts in), which the proposed unconditional preventDefault reverses with no opt-out — a fact the item's own "could regress" section concedes. The minimal fix for the verified defect (a dead `button === 1` guard plus a comment describing behaviour that cannot happen) is to DELETE `handleContextMenu` and the `onContextMenu={handleContextMenu}` binding at :2239. Whether the library should suppress belongs with the Ctrl+click sign-off already filed at report line 543, not in this commit.

2. **(c)'s user-visible claim is overstated on macOS.** All three additive-select sites read `e.ctrlKey || e.metaKey` (:1741, :1882, :1897), so Cmd+click — the platform-native additive chord on macOS — works and does not fire contextmenu. Ctrl+click on macOS IS the platform-native right-click, so a menu appearing there is arguably correct. "Multi-selecting on a Mac pops the OS menu on top of the selection" only holds for a user who deliberately picks the non-native modifier.

3. **(b)'s fix is much bigger than the defect and its justification is untestable here.** The verified defect is one dead line. The proposed remedy is a ~50-line handler relocation carrying two regression modes the item names itself, including the C23 stale-closure class in a brand-new listener. Its only justification is the assertion that `touchAction: 'none'` (:2229, already declared) fails to stop WebKit's visual-viewport pinch — asserted, not measured, and unmeasurable in this repo: `harness/behaviors.mjs` is chromium-only. It is also not obviously sufficient even if true, since iOS page pinch is driven by `gesturestart`/`gesturechange`, which nothing here touches. Either measure the iOS behaviour first, or take the one-line deletion and keep the relocation as a separate, evidence-backed change.

4. **(d)'s fix shape violates this repo's own #1 rule; a simpler one exists.** The proposal adds `useState` + a React re-render to `Minimap`, which CLAUDE.md bans in this file's class of code and which the item's own "could regress" flags. The minimal, rule-conformant fix is imperative: a `matchMedia('(resolution: Xdppx)')` listener (or `ResizeObserver` with `box: 'device-pixel-content-box'` on the canvas, hung on the observer already at minimap.tsx:679) that writes `canvas.width`/`canvas.height` and re-applies `ctx.scale` directly — no state, no render, and the width-before-scale ordering the item correctly insists on is preserved for free.

5. **(a)'s evidence contains one inversion and one overstatement.** Chrome-on-iOS matching the regex and receiving `antialias: false` is presented as a misfire, but Chrome-on-iOS is WebKit, so that is precisely the outcome the flag's stated intent wants — the regex reaches the right answer for the wrong reason there. The genuine misfire set is narrower than claimed: iOS in-app WebViews with no `Safari/` token. And "MSAA on the default framebuffer is buying nothing for anyone" is not literally true — `image-entities.tsx` draws hard-edged textured quads (`MeshBasicMaterial`/custom `ShaderMaterial`, no shader AA on the quad boundary), whose geometric edge at a fractional pixel is the one thing MSAA does sample. The effect is small, but the pixel proof the item already demands should be run against a scene containing image entities, not only SDF nodes.
