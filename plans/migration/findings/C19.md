## What a person experiences

Nothing is drawn wrong. What a person feels is GC: a sustained pan or drag on a large graph produces a steady stream of short-lived objects, and the measured baseline in plans/migration/audit-findings.md is ~9.4 KB/frame panning at 200 entities and ~35.6 KB/frame dragging at 2000. On a 60 Hz budget that is ~0.5–2 MB/second of garbage in the exact window where a dropped frame is visible as a stutter under the pointer. It is also a direct violation of the repo's own rule ("Pre-allocated buffers — no allocations during render"; "Zero React re-renders / no allocation in hot paths"), so today the codebase does not do what CLAUDE.md says it does. The double glyph-matrix write additionally costs a full memcpy of every visible glyph's 64 bytes per frame per font weight, which is CPU work rather than bytes.

## Proposed fix

Six edits, smallest first. Land them as separate commits — they have different risk.

1. grid.tsx:119 — replace the spread with in-place field writes:
   `const last = lastViewportRef.current; last.x = viewport.x; last.y = viewport.y; last.zoom = viewport.zoom;`
   Exactly equivalent: the object is only ever read field-by-field at :111-113 and nothing else holds it.

2. kookie-flow.tsx:2154 — move the `Array.from` inside its own guard. Replace lines 2154-2156 with
   `if (touchState.current.touches.size === 2 && touchState.current.initialDistance !== null) { const touches = Array.from(touchState.current.touches.values()); ...`
   and close the brace where the existing `if` closed. `touches` is read nowhere outside that block.

3. accent-colors.ts — kill both allocations without changing the exported signature. Add a module-scope key table built once from the closed `AccentColor` union (types/index.ts:691-717):
   `const ACCENT_TOKEN_KEY = { gray: '--gray-9', gold: '--gold-9', ... } as const satisfies Record<AccentColor, keyof ThemeTokens>;`
   and add a hot-path entry point that writes into the buffer instead of returning an array:
   `export function writeAccentColorRGB(color: AccentColor | undefined, tokens: ThemeTokens, out: Float32Array, offset: number): void` — writes `-1,-1,-1` when `!color`, else `out[offset+i] = value[i]`. Keep `resolveAccentColorRGB` as-is for the (internal-only) barrel export.
   Then nodes.tsx:470-473 collapses to `writeAccentColorRGB(entity.color, tokens, bufs.accentColor, idx * 3);`.
   Do NOT "fix" it by returning `value` directly — that hands the caller the theme's own array and one mutation corrupts the palette for every entity.

4. The double glyph-matrix write, text-renderer.tsx:187 and text-entities.tsx:169 — pass the mesh's own array as the `matrices` argument and delete the intermediate. In text-renderer.tsx:174-187:
   `const glyphCount = populateGlyphBuffers(entries, fontMetrics, glyphMap, kerningMap, mesh.instanceMatrix.array as Float32Array, buffers.uvOffsets, buffers.colors, buffers.opacities, capacity);`
   then drop the `.set(...subarray(...))` line, keeping `mesh.instanceMatrix.needsUpdate = true` and `mesh.count = Math.min(glyphCount, capacity)`. Delete `matrices: new Float32Array(capacity * 16)` from the `buffers` useMemo (text-renderer.tsx:108, text-entities.tsx:96). Same edit in text-entities.tsx with `populateMultiLineGlyphBuffers`. Sizes already agree: `args={[geometry, material, capacity]}` with `key={capacity}` means three allocates `instanceMatrix` at exactly `capacity * 16`, and both populate functions `break` at `glyphIndex >= capacity`.

5. text-renderer.tsx / text-entities.tsx per-entity entries — two steps.
   (a) Free and safe: make `TextEntry.id` optional (text-layout.ts:136) and stop writing it at text-renderer.tsx:356, 416, 449, 491. Nothing in the package reads it; grep for `entry.id` in text-layout.ts returns nothing, and `TextEntry` is exported only from `utils/index.ts`, which the package `index.ts` does not re-export, so it is internal. That deletes one string per visible entity, per socket and per labelled edge, per frame.
   (b) Pool the entry objects. Hold `regularPool: TextEntry[]` and `regularCount` in refs; grow the pool on demand; mutate fields in place (including `position[0..2]`, which stops being reallocated at :358/:418/:451/:493). The child's change detector is `entries === lastEntriesRef.current` (text-renderer.tsx:158), which a pooled array defeats — replace it with a `collectVersionRef` the parent bumps and the child compares. Same shape in text-entities.tsx, whose child additionally reads `entry.id` (text-entities.tsx:184), so keep the id there.

6. edges.tsx:635/643 (and :518/:740) — build the two lookup keys ONCE per edge, not per frame. Add `sourceKeysRef: string[]` / `targetKeysRef: string[]` filled in the same place the socket index map is filled (edges.tsx:335-351 and the `unsubEdges` subscription at :372-378, since an edge's `sourceSocket` can change), and have the frame loop do `socketIndexMap.get(sourceKeys[i])`. Do NOT reshape `SocketIndexMap` — it is exported from the package `index.ts:46` and shared with text-renderer.tsx and four functions in utils/geometry.ts, so that is a public break and belongs in its own item.

Deliberately NOT fixed, per the audit's own instruction: dom-layer.tsx:176-179 must not gate `width`/`height`/`fontSize` on zoom — comments are resizable and the store signals it via `positionVersion`, so that gate freezes the box mid-resize. The safe version of that idea guards on the VALUE, not the axis: stash the last-written screenX/screenY/w/h/fontSize as numeric fields on the element and skip the string build when unchanged, which skips three of five writes during a pan and still writes during a resize because the value moved.

## What could regress

Per fix, and only two of the six carry real risk.

grid.tsx and kookie-flow.tsx: nothing. Both objects are read only where they are built. No existing law reads either. (The touch path is not covered by harness/behaviors.mjs at all, which is worth saying out loud — it is unguarded either way.)

accent-colors.ts + nodes.tsx: the hazard is the one I am avoiding rather than committing — returning the shared theme array would let any caller mutate the palette. With `writeAccentColorRGB` the risk is a wrong offset writing over a neighbour's accent (three floats, adjacent entity in the same buffer). The existing pixel instrument would catch it: the per-entity accent renders as a header tint (nodes.tsx fragment shader :238-240, `mix(bgColor, vAccentColor, 0.15)`), so a colour readback over a coloured node's header changes. The `ACCENT_TOKEN_KEY` table also becomes a second home for the `--${color}-9` convention — `satisfies Record<AccentColor, keyof ThemeTokens>` is what makes `tsc` fail if the union grows, which matters because the migration notes say `Entity.color` is being narrowed for v2.

The double glyph-matrix write is the dangerous one. Three ways it can go wrong, all of them "text vanishes or draws garbage": (a) the capacity-change window — `buffers` is memoised on `capacity` and `initializedRef.current = false` is set in the `[buffers]` effect (text-renderer.tsx:123-127), so writing to `mesh.instanceMatrix.array` before the new mesh has attached would target the OLD mesh's array at the OLD length; the existing `if (!mesh || !initializedRef.current) return` guard is what holds this, and it must not be reordered. (b) three's `instanceMatrix.array` is typed `TypedArray`; the cast to `Float32Array` is load-bearing and is only correct because `InstancedMesh` allocates `new Float32Array(count * 16)`. (c) Today the copy only writes the live prefix and leaves the tail stale, but `mesh.count = safeGlyphCount` means the tail is never drawn — writing directly preserves that exactly, so nothing changes, but any future change that draws past `count` would now show different garbage.

The entry pooling is the second dangerous one, and specifically the change detector. `TextWeightRenderer`/`TextEntityWeightMesh` skip all work when `entries === lastEntriesRef.current` (text-renderer.tsx:158, text-entities.tsx:139). Pool the array and that comparison is true forever: text freezes at whatever it said on the first frame, and every existing behaviour law that reads text pixels would keep passing during idle and fail only mid-drag. Replace the identity check with an explicit version in the SAME commit, never after. `SENTINEL_ENTRIES` (text-renderer.tsx:49) exists to force a repopulate after a resize and its job has to be taken over by the version counter too.

edges.tsx key caching: the cache must be invalidated on BOTH triggers, not just one. `unsubEntitiesLength` (edges.tsx:358) rebuilds the socket map on add/remove, but `unsubEdges` (edges.tsx:372) fires when an edge's own `sourceSocket`/`targetSocket` changes without any entity count change. Invalidate on the second and a rewired edge keeps drawing to its old socket row — the exact class of defect b8e8169 just finished fixing.

Cross-cutting: every one of these is inside a `useFrame`, and C18 rewrites the same two `useFrame` bodies in text-renderer.tsx and text-entities.tsx. Landing C19's item 4/5 first means C18 rebases onto a changed function.

## The law that proves it

The law must NOT be "alloc B/f goes down", and the repo has already recorded why: plans/migration/audit-findings.md, on fix 17 — "the allocation column drifts in both directions (drag-node 4,974 -> 5,245 B/f, pan 9,364 -> 8,697) — variance in a 4096-byte heap sampler over a short window on a shared machine, not a result." A before/after byte delta on this instrument is fitted to noise.

THE LAW — a scaling law, in a new `harness/spikes/allocations.mjs` run as an assertion rather than a report, built on `counts.mjs`'s existing `measure()` and its `byFunction` walk of `HeapProfiler` samples.

The claim under test is "per VISIBLE entity", and the fixture is chosen so the general case and the special case give different answers. `makeGraph` (harness/fixture/graph.ts:67-69) lays entities on a fixed 320x220 grid, so at a fixed viewport the number of entities ON SCREEN does not change with `count` — which is why the existing 200-vs-2000 pan numbers say nothing and why a total-count scaling law would be a law about the wrong axis. Instead hold the graph at `count=2000` and vary ZOOM: pan 60 pointermoves at `zoom = 1.0` (~14 entities in view) and again at `zoom = 0.4` (~85 in view; deliberately above `MIN_SOCKET_ZOOM = 0.35`, text-renderer.tsx:58, so socket labels are still being collected in both runs and the two runs differ ONLY in how many entities are visible).

Assert two things, one absolute and one relative:
  A. `bytesFrom('resolveAccentColorRGB' | 'accent-colors.ts')` and `bytesFrom('collectTextEntries' | 'text-renderer.tsx')` are 0 in both runs.
  B. `allocBytesPerFrame(zoom 0.4) <= allocBytesPerFrame(zoom 1.0) * 1.5`. Six times the entities may not cost six times the bytes.

Two vacuity guards, in `counts.mjs`'s own "INSTRUMENT DEAD ... Refusing to report" style (spikes/counts.mjs:143-160), because "the function does not appear in the profile" is exactly what a profiler that resolved nothing also reports:
  - refuse to report unless the sample tree names at least one call frame whose url is the fixture bundle, i.e. the profiler is resolving app frames at all;
  - refuse to report unless `visibleEntityCount(zoom 0.4) >= 4 * visibleEntityCount(zoom 1.0)`, read from the store through `window.__harness`, so the law cannot silently pass by comparing two identical scenes.
Sample at 512 bytes, not 4096: the fixed cost is irrelevant here (nothing is timed) and the resolution is the whole point.

THE SABOTAGES. Each must make exactly its own assertion fail, run one at a time, and each reverted by inverse edit (never `git checkout` — that discards uncommitted work):
  - accent-colors.ts:39 — put `return [value[0], value[1], value[2]];` back. Assertion A must fail naming `accent-colors.ts`. Expected volume: 2000-entity graph, ~85 visible x 60 frames x ~40 B = ~200 KB, ~400 samples at 512 B — orders above the sampler floor, so a pass here is not luck.
  - accent-colors.ts:34 — put `` const tokenKey = `--${color}-9` `` back with the array fix kept. A must fail again. Run this one SEPARATELY: if it does not fail while :39 does, V8 has folded the string and the law is a law about the array only, and must say so.
  - text-renderer.tsx:358 — put `position: [entity.position.x + 12, labelY, 0.1]` back on the entry. A and B must both fail.
  - grid.tsx:119 — put `lastViewportRef.current = { ...viewport };` back. This one allocates once per FRAME, not per entity, so it must NOT move assertion B — and if it does, B is reading frame count rather than visible count and is broken. It is checked instead by a third assertion: `bytesFrom('grid.tsx') === 0`.
  - text-renderer.tsx:187 — put `mesh.instanceMatrix.array.set(buffers.matrices.subarray(0, safeGlyphCount * 16));` back. This is the one the sampler is WEAK on: a `subarray` view is ~100 bytes and the memcpy allocates nothing at all, so the byte law will very likely survive this sabotage. That is the finding, not a failure — and it is why the double write needs a different law: patch `Float32Array.prototype.subarray` from the page before the gesture, count the calls, and assert zero bulk matrix copies during a pan (pre-fix: one per weight per dirty frame). Pair it with the existing text-pixel behaviour laws in harness/behaviors.mjs and harness/spikes/label-zoom.mjs unchanged, because the risk of writing straight into `instanceMatrix.array` is that the text disappears, and a byte counter cannot see that.

Two things must be true for any of this to count. First, the same sabotage-and-revert discipline the socket-geometry work recorded: a fix accepted without its sabotage failing first is a guess. Second, if a sabotage SURVIVES, the honest move is to say the law is about something narrower than its name (the repo's own "a law over a general case must be built on an input where the general case and the special case give different answers"), not to widen the threshold until it goes red.

## What the critics said

### exists

Two nits, neither affecting the finding. (a) The finding's parenthetical "the two in core/store.ts:903,926" is accurate but worth stating precisely: 903 is the `...viewport,` line inside `pan` (899-906), 926 is `viewport: { ...viewport, zoom: newZoom }` in `zoom`; `zoom`'s centred branch (916-922) builds a fresh literal with no spread, and `setViewport` (609) is `set({ viewport })`. (b) For sub-item (4) it is worth recording explicitly in the fix commit that the two arrays are provably distinct (the init effects never reassign `mesh.instanceMatrix`), since that is the fact that makes the copy real and the fix safe.

### safety

Two of the six proposed edits are unsafe AS SKETCHED, and one magnitude claim is overstated.

(a) Item 3 introduces a per-frame crash. The sketch specifies writeAccentColorRGB as "writes -1,-1,-1 when !color, else out[offset+i] = value[i]", which drops the `Array.isArray(value) && value.length >= 3` guard at accent-colors.ts:37. There is NO runtime validation of entity.color anywhere in the package (grep for isAccentColor / normalizeEntity / ACCENT_COLORS returns nothing; it is only typed at types/index.ts:371). Today an entity carrying an unknown colour string from JSON gets console.warn plus the sentinel and renders with the global accent. Under the sketch ACCENT_TOKEN_KEY[bad] is undefined, tokens[undefined] is undefined, and value[0] throws a TypeError inside useFrame every frame — R3F does not catch frame-loop errors, so the canvas dies. The table itself is fine: all 26 union members exist as `--{color}-9` in both the ThemeTokens interface and FALLBACK_TOKENS (verified), so the token can never be missing for a valid colour. Keep the unknown-key guard.

(b) Item 5b is under-specified at four sites, not one. The sketch names only the `entries === lastEntriesRef.current` detector, but `entries.length` IS the live count today and is read by countGlyphs/countMultiLineGlyphs, populateGlyphBuffers/populateMultiLineGlyphBuffers, the `entries.length === 0 -> mesh.count = 0` branch, and — unnamed by the finding — text-entities.tsx:180-188, which loops `for (const entry of entries)` and sets `mesh.renderOrder = hasSelected ? FG : BG` from `selectedEntityIds.has(entry.id)`. A pool whose .length exceeds the live count draws ghost glyphs at stale positions AND flips a whole text mesh's z-order off a culled-but-still-pooled entity. A live-count channel must reach the child's props and both exported populate/count helpers; truncating the pool per frame instead gives back most of the win during a pan, which is exactly when the visible count oscillates. The LOD path compounds it: text-renderer.tsx:557-563 hides text below MIN_TEXT_ZOOM purely by assigning a fresh [], and MultiLineTextEntry.lines is a fresh array from wrapTextMSDF every frame regardless of pooling.

Nothing in the harness would catch either regression: behaviors.mjs has exactly one text law (:178, "no label is a DOM element") which asserts text is ABSENT from the DOM and passes with GL text frozen, ghosted or gone; label-zoom.mjs asserts nothing (its only process.exit is the fixture-missing guard at :31); counts.mjs's process.exit(3) at :157 is an instrument-calibration check, not an allocation assertion. The finding is right that this is unguarded, which also means the pooling commit would ship its own regression green.

(c) Magnitude. The user-visible paragraph attributes the ~9.4 KB/frame pan and ~35.6 KB/frame drag to these sites. plans/migration/audit-findings.md:169-172 names the measured top allocators for the 35.6 KB drag row as `set`, `insert`, `getKey`, `rebuildDerivedState` and `buildAdjacencyIndex` — the store's derived-state rebuild (T4) — not any C19 site, and :176 records that React commits are 2-4 per GESTURE so the "zero re-renders during interactions" rule is not the one being violated (the no-allocation-in-hot-paths rule is). The pan row also FALLS from 9,364 to 3,186 B/f going 200 -> 2000 entities, which is not the shape a per-visible-entity allocation produces. The C19 sites are real and live, but they are not the dominant term in that table.

### minimal

Four things are wrong or overstated, and they change what should be committed.

1. THE USER-VISIBLE NUMBERS ARE MISATTRIBUTED. Both figures are lifted from the baseline table in plans/migration/audit-findings.md, and that same document names the top allocators behind them. For drag @2000 (35,646 B/f) it says they are `set`, `insert`, `getKey`, `rebuildDerivedState` and `buildAdjacencyIndex` — the T4 controlled-component contract rebuilding derived state. For pan it says outright: "what does appear under pan is React's own synthetic event machinery." Not one function C19 names appears in any top-6 allocator list at either graph size. Note also pan alloc/frame FALLS from 9,364 @200 to 3,186 @2000 while the visible-entity count is roughly fixed at a 1280x800 viewport — the opposite of what a per-visible-entity allocation would do. Fixing all six items moves neither headline number materially. The honest claim is rule-compliance plus the glyph memcpy, not "~0.5-2 MB/second of garbage in the window where a dropped frame is visible."

2. SUB-ITEM (1) ALLOCATES ZERO IN EVERY MEASURED RUN, AND STILL WILL AFTER THE FIX. `harness/fixture/graph.ts` sets `color` on no entity (grep for "color" in that file returns nothing), so `resolveAccentColorRGB` takes the `!color` branch and returns the module-scope sentinel — no string, no array. It is real in an app with coloured nodes, but it has never been measured and the existing instrument cannot show the fix working. Say that rather than implying the fix buys measured bytes.

3. ITEM 3'S FIX IS NOT MINIMAL, AND IT CREATES THE SECOND HOME THIS REPO'S OWN T2 LESSON IS ABOUT. `tokens` is `useState` state (useThemeTokens.ts:497) replaced only when `tokensEqual` (:515-529) reports a real change, so its identity is stable across every frame of a pan or drag. That makes a six-line, single-file cache sufficient: a module-scope `lastTokens` plus `Map<AccentColor, RGBColor>`, cleared on identity change, returning the cached tuple. It removes BOTH allocations, changes no call site, adds no export, and — unlike returning `value` directly, which the finding rightly refuses — still hands out an array the theme does not own. The proposal instead ships `writeAccentColorRGB` ALONGSIDE `resolveAccentColorRGB` (two homes for one resolution, the survivor reachable only through a barrel `src/index.ts` never re-exports) plus a 30-entry `ACCENT_TOKEN_KEY` table duplicating the `--${color}-9` convention. Also unflagged: accent-colors.ts:42 `console.warn` fires per entity per frame on an unknown token — a template string and a console call every frame, strictly worse than the allocation being fixed. Whatever shape the fix takes, warn once.

4. ITEM 5 IS WRONG ABOUT text-entities.tsx, AND ITEM 6 IS ADMITTED SCOPE CREEP. text-entities.tsx:402 and :422 write `id: entity.id` — the raw id, no template literal — so there is no per-entity string there, only the position 3-array; and `entry.id` IS read at :184 (`selectedEntityIds.has(entry.id)`). "The same shape at a bigger scale" overstates it twice over: text entities are only `entity.type === 'text'`, a small subset, where text-renderer.tsx covers every visible entity, socket and labelled edge. Only text-renderer.tsx:356/416/449/491 allocate strings. And the finding itself says edges.tsx:635/643/586 are "NOT in its five bullets" — bundling them makes C19 a six-file change carrying the rewire-invalidation hazard the finding correctly identifies, which is the exact defect class b8e8169 just closed. They belong in their own item.

RECOMMENDED SCOPE: land items 1, 2 and 4, plus a six-line cache for 3. Item 4 is the only one with real CPU cost (a full memcpy of every visible glyph's 64 bytes per frame per weight) and its fix is exactly minimal. Defer item 5 to whoever does C18 — the finding's own last line says C18 rewrites the same two useFrame bodies, and item 5 is the one that must replace the `entries === lastEntriesRef.current` detector in the same commit or text silently freezes mid-drag. Defer item 6 to its own item. Sell 1 and 2 as rule-compliance (a few tens of bytes per frame, and two allocations per one-finger touchmove on a path no law covers), not as perceptible perf.
