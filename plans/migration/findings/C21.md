# C21 — risk medium, proof behaviour-browser, depends on nothing

## Is it still there

Not in the fixed list: `plans/migration/audit-findings.md` names 17 landed fixes and `dom-layer` appears in none of them (`grep -n dom-layer plans/migration/audit-findings.md` → no match). The file is unchanged from what the audit described.

**The change detector is the comment COUNT** — `src/components/dom-layer.tsx:200-211`:
```ts
    const unsubEntities = store.subscribe(
      (state) => state.entities,
      (entities) => {
        const currentComments = entities.filter(
          (n): n is Entity<CommentEntityData> => n.type === 'comment'
        );
        if (currentComments.length !== commentEntities.length) {
          setCommentEntities(currentComments);
        }
        scheduleUpdate();
      }
    );
```
So React re-renders only when the number of comments changes.

**Everything presentational is rendered by React and only by React** — `dom-layer.tsx:273-293`:
```tsx

        const data = entity.data as CommentEntityData;
```

**The imperative path never writes any of it** — `dom-layer.tsx:170-182`, the whole write set per comment per frame:
```ts
      const baseFontSize = parseFloat(el.dataset.baseFontSize ?? String(DEFAULT_COMMENT_FONT_SIZE));
      const scaledFontSize = baseFontSize * viewport.zoom;

      el.style.visibility = 'visible';
```

No `textContent`, no `backgroundColor`, no `color`. And `fontSize` is doubly stale: it reads `el.dataset.baseFontSize`, an attribute React wrote once at mount, so `data.fontSize: 14 → 28` still paints `14 * zoom`.

**The store does deliver the change; only the reader is broken.** `store.ts:753-757` `case 'data'` builds `{ ...entity, data: { ...entity.data, ...change.data } }`, `rebuildDerivedState` (store.ts:398-406) rebuilds `entityMap` from the fresh array, and `set({ entities: nextEntities, ...derived })` (store.ts:776-780) publishes a new `entities` reference — so `unsubEntities` fires and `scheduleUpdate()` runs. The imperative path executes with the fresh entity in hand at `dom-layer.tsx:132` (`const entity = entityMap.get(entityId)`) and reads nothing from it but `width`, `height`, `position`, `type`.

**The count detector fails a second way: an equal-count swap.** `applyEntityChanges([{type:'remove', id:'c1'}, {type:'add', entity: c2}])` (store.ts:690, 708) leaves the count at 1, so no re-render happens: `commentsRef` still holds c1's div, `entityMap.get('c1')` is `undefined`, and `dom-layer.tsx:133-135` hides it — while c2 gets no element at all. Both comments are invisible.

**Contrast — width/height DO track**, because they are read live at `dom-layer.tsx:144-145` (`entity.width ?? DEFAULT_COMMENT_WIDTH`) and `updateEntityDimensions` (store.ts:1099-1101) bumps `positionVersion`, which `unsubPositions` (dom-layer.tsx:220-223) subscribes to. That is what the audit's C19 note is protecting.

**Zero coverage.** No `dom-layer` test file exists (`find src -name '*.test.*'` lists nine files, none of them a component under `components/` except `interaction-state.test.ts`), and `harness/behaviors.mjs` contains no `comment` — the fixture (`harness/fixture/graph.ts`) creates no comment entity of any kind, so all 37 behaviours and 196 unit laws are green over this.

## What a person experiences

A comment (sticky note) shows the words, background colour, text colour and font size it had at mount, for the life of the mount. A consumer app that edits a comment — through `onEntitiesChange`/`applyEntityChanges` or by pushing a new `entities` prop — sees the note redraw its box and move with the canvas while its text, colour and size never change. Resizing and dragging work; editing does not.

Worse in one case: replacing one comment with another in a single change batch (remove c1 + add c2, count unchanged) makes BOTH invisible — the old element is hidden because its id is gone from `entityMap`, and the new comment never gets an element. The sticky note vanishes with no error.

Comments are the last persistent DOM over GL, so this is the only surface in the package where DOM text can be stale at all.

## Proposed fix

Two edits, both in `src/components/dom-layer.tsx`. Do NOT use a reference compare of the filtered array (the audit's explicit warning): `entities.filter(...)` at :203 allocates fresh on every store change and `updateEntityPositions` republishes `entities` on every pointermove, so that spelling re-renders once per drag frame.

**1. Move presentation into the imperative path** (owns per-frame updates, zero allocation, zero re-render). Replace `dom-layer.tsx:170-173`:
```ts
      const baseFontSize = parseFloat(el.dataset.baseFontSize ?? String(DEFAULT_COMMENT_FONT_SIZE));
      const scaledFontSize = baseFontSize * viewport.zoom;
```
with:
```ts
      const data = entity.data as CommentEntityData;
      const content = data.content ?? '';
      if (el.textContent !== content) el.textContent = content;      // guard is load-bearing, see couldRegress
      const bg = data.backgroundColor ?? DEFAULT_COMMENT_BG;
      if (el.dataset.bg !== bg) { el.dataset.bg = bg; el.style.backgroundColor = bg; }
      const fg = data.textColor ?? DEFAULT_COMMENT_TEXT_COLOR;
      if (el.dataset.fg !== fg) { el.dataset.fg = fg; el.style.color = fg; }
      const baseFontSize = data.fontSize ?? DEFAULT_COMMENT_FONT_SIZE;
      const scaledFontSize = baseFontSize * viewport.zoom;
```
The `dataset.bg`/`dataset.fg` shadow exists because `el.style.backgroundColor` serialises (`'#FFF9C4'` → `'rgb(255, 249, 196)'`), so comparing against the raw token never matches and the guard would never hold. Then strip the now-dead writers from the JSX at :283-290 — delete `data-base-font-size={fontSize}`, `backgroundColor: bgColor`, `color: textColor` and `{data.content}` — so each property has exactly one owner. First paint is still correct: ref callbacks run before layout effects, and `useLayoutEffect` at :195-196 calls `updateComments()` synchronously before paint.

**2. Make the structural detector identity, not count.** At `dom-layer.tsx:206`, replace the length compare with a pairwise id compare against a ref (`const commentIdsRef = useRef<string[]>([])`):
```ts
        const prev = commentIdsRef.current;
        let changed = currentComments.length !== prev.length;
        if (!changed) {
          for (let i = 0; i < currentComments.length; i++) {
            if (currentComments[i].id !== prev[i]) { changed = true; break; }
          }
        }
        if (changed) {
          commentIdsRef.current = currentComments.map((c) => c.id);
          setCommentEntities(currentComments);
        }
```
O(#comments) string compares per store change, allocating only when the set actually changed. The closure then no longer reads `commentEntities`, so `commentEntities.length` can leave the dep array at :253 — which also stops the effect tearing down and re-subscribing all four subscriptions every time a comment is added or removed.

**3. One attribute the law needs:** add `data-entity-id={entity.id}` to the div at :280 so a law can select a specific comment and assert WHICH comment an element is. Without it the swap case is unassertable — there is one div before and one after either way.

## What could regress

**Live text selection — this is the sharp edge.** `commentStyle` sets `pointerEvents: 'auto'` and `userSelect: 'text'` (`dom-layer.tsx:312-314`), so a user can select comment text today. `updateComments` runs on every viewport change, i.e. every pan and zoom frame. Writing `el.textContent = content` unconditionally would collapse the selection on every one of those frames. The `if (el.textContent !== content)` guard is therefore correctness, not an optimisation, and must not be "simplified away". (Finding #122 proposes moving comments to GL entirely, which would retire this; until then the guard stands.)

**Re-render count during drag.** The forbidden spelling — comparing `currentComments` by reference — is the one the audit calls out by name. `updateEntityPositions` (store.ts:1049-1050) publishes `nextEntities` on every pointermove, and `entities.filter(...)` allocates a fresh array each time, so a reference compare produces one React commit per frame. The existing `T-count` React commit counter catches it.

**Collision with C19, textual not logical.** C19's batch also touches `dom-layer.tsx` and its plan note says: *"do not gate width/height/fontSize on zoom as filed; comments are resizable and the store signals it via `positionVersion`, so that gate freezes the box mid-resize."* After this fix that warning gets stronger, not weaker: `fontSize` now sources from `data.fontSize`, which changes with no zoom change at all, so a zoom gate would freeze the font size too. Whichever lands second must rebase over the other inside `updateComments`.

**Two owners of one property.** If the JSX keeps `backgroundColor`/`color`/`{data.content}` alongside the new imperative writes, React wins on any structural re-render and the imperative path wins on the next microtask — the value flickers between two sources and neither file is wrong on its own. Delete the JSX copies in the same commit.

**Whitespace.** `commentStyle` sets `whiteSpace: 'pre-wrap'`; `el.textContent = content` reproduces React's `{data.content}` output exactly for a string, and `CommentEntityData.content` is typed `string` (`types/index.ts:208`), so there is no array-children or number-coercion case to lose.

## The law that proves it

Three laws in `harness/behaviors.mjs`, driving the real store through `window.__harness.store`. All three need one fixture addition — no scene in `harness/fixture/graph.ts` creates a `type: 'comment'` entity, so add a comment (id `c1`, explicit `content`, `backgroundColor`, `textColor`, `fontSize`) to `makeShapes()` or a new `scene=comment`.

**Law A — content, colour and size track the store.**
Select `[data-entity-id="c1"]`. Snapshot `el.textContent`, `getComputedStyle(el).backgroundColor`, `.color`, `.fontSize`, and `document.querySelectorAll('[data-entity-id]').length`. Then:
```js
store.getState().applyEntityChanges([{ type: 'data', id: 'c1',
  data: { content: 'edited', backgroundColor: '#00ff00', textColor: '#ff0000', fontSize: 28 } }]);
```
await a microtask and a rAF. Assert: element count UNCHANGED (proves the update was not a remount), `textContent === 'edited'`, `backgroundColor === 'rgb(0, 255, 0)'`, `color === 'rgb(255, 0, 0)'`, and `fontSize === (28 * viewport.zoom) + 'px'`.

Read `getComputedStyle(el)` — never `el.style.fontSize`, and above all never `el.dataset.baseFontSize`. The dataset attribute IS the stale declared value at the centre of this defect; a law that reads it is one indirection short of the thing that is wrong, and would report `14` while claiming to measure the painted size.

**Vacuity guard, required:** assert the pre-change values differ from the post-change ones. The unset-field defaults (`DEFAULT_COMMENT_BG` `#FFF9C4`, `DEFAULT_COMMENT_TEXT_COLOR` `#424242`, `DEFAULT_COMMENT_FONT_SIZE` 14) are exactly what a fixture leaving those fields unset resolves to, so "changing" `backgroundColor` to `#FFF9C4` measures nothing and passes against the defect.

**Law B — the general case, not the special case.** Law A alone is satisfiable by a fix that watches `data` and still keys structure off length. So, in ONE call:
```js
store.getState().applyEntityChanges([
  { type: 'remove', id: 'c1' },
  { type: 'add', entity: { id: 'c2', type: 'comment', position: {x:...,y:...},
                           data: { content: 'second' } } },
]);
```
Count stays 1. Assert exactly one comment element exists, its `data-entity-id === 'c2'`, its `textContent === 'second'`, and `getComputedStyle(el).visibility === 'visible'`. Asserting only "one element exists" passes against the defect and is the degenerate version of this law.

**Law C — the fix costs no renders.** `__harness.mark('drag')`, drive 60 real pointermove steps dragging a node, then assert `reactCommits().marks.drag` is unchanged from the pre-fix baseline.

**THE SABOTAGES, each of which must make exactly its own law fail:**

- *Law A, whole:* restore `dom-layer.tsx:172` (`parseFloat(el.dataset.baseFontSize ?? ...)`) and put `{data.content}`, `backgroundColor`, `color` back in the JSX while deleting the three imperative writes. Expected: `textContent` still the original string, background still `rgb(255, 249, 196)`, fontSize still `14 * zoom`.
- *Law A, partial — the one that matters:* revert ONLY the `textContent` write and keep both colour writes. The law must fail on the text assertion alone. This is what catches a law that asserts colour and calls itself "content tracks its content".
- *Law A, font only:* revert only `const baseFontSize = data.fontSize ?? ...` back to the dataset read. Fails on `fontSize` alone — and is the sabotage a `el.dataset.baseFontSize`-reading law survives, which is why the law must read `getComputedStyle`.
- *Law B:* restore `if (currentComments.length !== commentEntities.length)` at :206. Expected failure: the surviving element reports `data-entity-id="c1"` and `visibility: "hidden"`, with `c2` absent from the DOM.
- *Law C:* replace the id compare with `if (currentComments !== commentIdsRef.current) setCommentEntities(currentComments)`. Expected: `marks.drag` goes from 0 to ~60.

## What the critics said

### exists

One nuance in the write-up overstates the lifetime: the JSX (and therefore content, colours and `data-base-font-size`) DOES refresh whenever the comment COUNT changes — i.e. when any other comment is added or removed. So the freeze is "until the number of comments changes", not "for the life of the mount". This matters for the law: a fixture that adds or removes a second comment after the data edit will see correct text and hide the bug, so the law must edit a comment's data with the comment set held constant.

### safety

Two corrections to the proposed fix; the defect and step 1 stand.

(1) DO NOT remove `commentEntities.length` from the useLayoutEffect deps at dom-layer.tsx:253, as step 2 recommends. `updateComments()` at :196 is the ONLY post-commit painter — `scheduleUpdate()` queues a microtask, and the length dep is what re-runs the paint AFTER the React commit. FlowSync (kookie-flow.tsx:2377-2382) pushes the controlled `entities` prop from a `useEffect`, not a `useLayoutEffect`; React sets DefaultEventPriority while flushing passive effects, so `setCommentEntities` lands on DefaultLane and renders via the Scheduler's MessageChannel macrotask — after the microtask. Sequence with the dep removed: subscription fires, microtask `updateComments` runs with the new element not yet in commentsRef (and on the 0->1 case returns early at `if (!container)`, :110), React then commits a div that is `visibility:'hidden'` from commentStyle and — because step 1 deletes `{data.content}` from the JSX — also empty, and nothing calls updateComments again. The comment never paints, text or position, until an unrelated pan/zoom/drag/selection. The plan's "first paint is still correct" argument covers the initial mount only. The store-change-inside-a-React-event path happens to work (SyncLane flushes before microtasks), so this is lane-priority-dependent, which is itself reason not to rely on it.

(2) The plan's headline swap case is only half-fixed either way. An equal-count remove+add changes identity but not `commentEntities.length`, so the effect does not re-run even with the dep kept: c2's div mounts hidden and blank and stays that way until an unrelated event. Identity detection needs a matching post-commit paint — depend on the `commentEntities` array itself (a fresh reference only when identity changed) rather than its `.length`, or add a dep-less layout effect that calls `updateComments()` on every commit.

(3) Smaller: `useRef<string[]>([])` is seeded empty while `commentEntities` is seeded from `store.getState()`, so the first entity publish after mount sees a length mismatch and fires a spurious `setCommentEntities`. If that publish is a pointermove, that is a React commit during a drag — the project's #1 rule — and the T-count spike cannot see it because the fixture has no comment entity. Seed the ref from the same initializer as the state.

(4) Also note widgets-layer.tsx:424 uses the identical count detector (`prev.length !== entitiesLen`); this fix does not reach it, so the same class of freeze remains next door.

### minimal

Three corrections, none of which retire the finding.

**1. The user-visible claim is understated: the package's OWN toolbar is what goes dead.** `BUILTIN_DEFAULTS.comment = ['backgroundColor', 'textColor', 'fontSize']` (toolbar.tsx:109), and `textColor` (:850) and `fontSize` (:769) each render a real control calling `batchUpdate`, which emits `{type:'data'}` changes through `onEntitiesChange` (toolbar.tsx:164-177). So selecting a sticky note in the shipped UI and changing its text colour or font size does nothing visible. This is not "a consumer app that edits a comment" — it is the library's own selection toolbar.

**2. Overstated in one place: `backgroundColor`.** `BuiltInWidget`'s switch has no `case 'backgroundColor'` — it falls to `default: return null` (toolbar.tsx:888-889), so that widget renders nothing at all today. Background colour is a separate defect (declared widget, no implementation) and is only reachable through a consumer's own data change. Do not cite the background-colour picker as evidence for C21.

**3. The one over-reach in the proposed fix: do NOT drop `commentEntities.length` from the effect deps at :253.** The proposal offers this as a free bonus ("stops the effect tearing down and re-subscribing"). It is load-bearing twice. `CommentsContainer` returns `null` when there are no comments (:258), so on a graph that starts with zero comments `containerRef.current` is null when the layout effect first runs — `containerRef.current?.parentElement` is undefined and the **ResizeObserver is never attached**, leaving `cachedSizeRef` at `{0,0}` for the life of the mount. Today the length dep re-runs the effect on the 0→1 transition, which attaches the observer and calls `updateComments()` synchronously after the new element has mounted. Remove it and (a) every comment added later culls against a zero-size viewport — `viewRight` collapses onto `viewLeft`, so anything past `viewLeft + 100` is hidden; and (b) the post-commit repaint is left to `queueMicrotask(updateComments)` racing React's commit, which it loses whenever the store change originates outside a React event handler (FlowSync's effect, a rAF, a timeout), so a newly added comment stays at its `visibility: hidden` default until the next pan. Keep the dep; the per-add resubscribe of four store listeners is cheap and rare.

Otherwise the fix as written is minimal and I verified its load-bearing details: `entityMap` is rebuilt from the fresh array on a data change so `entityMap.get(entityId)` at :132 does carry the new `data`; `CommentEntityData.content` is a required `string` (types/index.ts:208), so `el.textContent = content` reproduces `{data.content}` exactly under `whiteSpace: 'pre-wrap'`; the `if (el.textContent !== content)` guard really is correctness rather than optimisation, because `commentStyle` sets `userSelect: 'text'` (:314) and `updateComments` runs on every pan and zoom frame; and the `dataset.bg`/`dataset.fg` shadow is needed because `el.style.backgroundColor` serialises to `rgb(...)`. The fix also owes a fixture change, since the harness has no comment entity to drive.
